## 1. 要点

セルフホスト型の Git サービス Gitea の公式 Docker イメージは、すべての送信元を信頼したリバースプロキシと見なす設定を既定にしていた。そのため、リバースプロキシ認証が有効な構成では、どこから届いた要求でも、`X-WEBAUTH-USER: admin` のヘッダーを付けるだけで管理者として認識された。認証情報は要らず、ほかの前提条件も無かった。Gitea は 1.26.3 で修正し、リバースプロキシ認証を明示的に有効にする方式に改めた。<strong>誰が送ったかを要求の中の値だけで決める仕組みでは、その値を書ける相手なら誰でも、その人として操作できる。</strong>

## 2. 通った操作

- **通った操作**: 保護されたエンドポイントへの、`X-WEBAUTH-USER: admin` のヘッダーを付けた要求と、それによる管理者としての認識・特権操作の許可。既定の `REVERSE_PROXY_TRUSTED_PROXIES = *` のため、送信元がリバースプロキシかどうかに関係なく、ヘッダーが認証済みの ID の主張として受け付けられた（Gitea・NVD）。
- **受け付けた側に届くもの**: 一般に、ヘッダーで伝えられる ID は、要求の中の文字列として届く。そのヘッダーを、利用者を認証したリバースプロキシが書いたのか、送り手が自分で付けたのかは、文字列からは区別がつかない。区別の手がかりは、要求がどの送信元から届いたかで、今回の既定の設定はその手がかりを使わなかった。
- **管理者に届いたあとに起こりうること**: すべての非公開リポジトリの閲覧、永続的なアクセスのための SSH 鍵の追加、以後のプッシュを外へ送る webhook の変更、CI/CD のシークレットの持ち出し、webhook を使った SSRF によるサーバー内部への到達。これらは想定される影響で、確認された被害ではない。
- **公表されていないこと**: 実環境で管理者の権限が取られたインスタンスがあったか。Sysdig は、開示 13 日後に初回の探索を検出したが、初期の調査の段階で、攻撃の進展には至っていないと報告した（The Hacker News）。露出した約 6,200 件のうち、リバースプロキシ認証が有効な構成がどれだけあったか。

## 3. 何を照合するか

経路を問わず区別できる条件は、管理者の権限で動く操作を実行する側が、その要求の主体が管理者であることを、要求の中に書かれた名前とは別に、実行の前に照合することである。

- **誰が承認を出すか**: Gitea の運用の責任者など、管理者の権限を誰に渡すかを決める担当者。SSH 鍵の追加・webhook の変更・設定の変更のような管理者の操作を、誰に、どの範囲で許すかを、サービスの外で決めておく。
- **どこで照合するか**: 二か所。ID を伝えるヘッダーを受け付ける手前で、要求が信頼したリバースプロキシから届いたかを照合する。管理者の操作を実行する手前で、主体がその操作を許された相手かを照合する。ヘッダーに管理者と書かれているだけの要求は、実行せずに止める。
- **何が残るか**: どの許可で、誰の要求が、どの管理者の操作として実行されたかの記録。要求がヘッダーを含んでいたという事実とは別に残す。

修正版の公開と探索の観測は、見つかった弱点と、その後の動きに対するもので、届いた要求の主体を管理者の操作の前に照合する仕組みではない。同じように、要求の中の値で認証が決まった事案に、[Starlette の BadHost](https://lemma.frame00.com/ja/critical/briefs/003-starlette-badhost/)（Host ヘッダーの操作で MCP サーバーの認証が外れた）と [Kestra の認証フィルターの回避](https://lemma.frame00.com/ja/critical/briefs/088-kestra-auth-filter-bypass-rce/)（パスの末尾を変えるだけで認証が外れた）がある。

## 4. Lemma でできること

**Lemma は、03 の照合を、管理者の権限で動く操作を実行する側に組み込む。** 弱点や侵入を見つけるのではなく、要求の主体がその操作を許された相手かを、ヘッダーに書かれた名前とは別に、実行の前に照合する。

### 注意したい業界・業務

- **業界 · 開発者・エージェント運用**: Gitea のようなセルフホスト型の開発基盤を、リバースプロキシの後ろで動かしている組織。ソースコード・CI/CD・開発者の ID が一か所に集まる。
- **業務 · アカウント・権限の管理**: SSH 鍵の追加、webhook の変更、管理者の設定の変更。ヘッダーに管理者と書かれていることだけでは、その操作を許された相手かは分からない。

### いまの対策と Lemma の違い

今回の弱点で確認されたのは 1 列目で、2 列目は、管理者として認識されたあとに起こりうる操作である。

| 対策 | 管理者を名乗るヘッダーつきの要求の受け付け（非公開リポジトリの閲覧を含む） | 管理者の操作（SSH 鍵の追加・webhook の変更） |
| --- | --- | --- |
| 修正版の適用（1.26.3／1.26.4・リバースプロキシ認証は明示的に有効にする方式） | 一部 | 関係しない |
| 信頼する送信元の最小化・リバースプロキシでのヘッダーの上書き・除去 | 一部 | 関係しない |
| 異常の検知（受け付けた後） | 効かない | 効かない |
| **Lemma（実行の前の照合）** | 効かない | 効く |

修正版の適用は、既定のすべての送信元の信頼を外すが、リバースプロキシ認証を有効にして信頼する送信元を広く取れば、同じ形の要求は通る。送信元の最小化とヘッダーの上書き・除去は、誰がヘッダーを書けるかを狭めるが、設定どおりに保たれていることが前提になる。異常の検知は、要求が受け付けられた後になり、受け付けた時点の管理者のアクセスは止まらない。Lemma は、要求の受け付けそのものは止めないが、SSH 鍵の追加や webhook の変更のような管理者の操作を、実行の前に、主体が許された相手かで照合する。実行の記録も残るので、要求がヘッダーを含んでいたという事実だけに頼らずに、どの操作が、どの許可で行われたかを確認できる。

注：Lemma の照合が働くのは、管理者の操作を実行する手前に照合を組み込み、許可の記録が Gitea の外で管理されている場合に限る。管理者として認識された要求でできる閲覧（非公開リポジトリの読み出しなど）は、この照合の外にある。表は何を照合しているかの比較で、今回の事案で止まったかどうかを示すものではない。Lemma は、侵入を検出・防止するものではない。

### 点検チェックリスト

リバースプロキシの後ろで動く開発基盤について、組織で確認する 3 項目

- Gitea の公式 Docker イメージが、1.26.4 以降になっているか。
- リバースプロキシ認証を使う場合、信頼する送信元が、実際のリバースプロキシだけに絞られているか。
- SSH 鍵の追加や webhook の変更が、いつ、誰の権限で行われたかの記録を、サービスの外で見られるか。

## 5. 事実と時系列

- **対象**: Gitea（セルフホスト型のオープンソースの Git サービス）。ソースコード・CI/CD・開発者の ID を集める開発基盤として広く使われる。
- **識別子**: CVE-2026-20896。Gitea 1.26.3 のセキュリティ修正の一つとして公開された。
- **深刻度**: CVSS 9.8（Critical、AV:N/AC:L/PR:N/UI:N/C:H/I:H/A:H）。CNA である Gitea の評価で、NVD 自身の再評価は本稿の時点で示されていない。
- **報告と修正**: 報告は Tenable の Joshua Martinelle と @rz1027、修正は @bircni。
- **手口の核心**: 公式 Docker イメージが `REVERSE_PROXY_TRUSTED_PROXIES = *` を既定にし、すべての送信元 IP を信頼したリバースプロキシとして扱っていた。リバースプロキシ認証が有効な構成では、保護されたエンドポイントへの要求に `X-WEBAUTH-USER: admin` を付けるだけで、管理者として認識された。
- **想定される影響**: すべての非公開リポジトリの閲覧、SSH 鍵の追加による永続的なアクセス、以後のプッシュを外へ送る webhook の変更、CI/CD のシークレットの持ち出し、webhook を使った SSRF によるサーバー内部への到達。
- **影響を受けるバージョン**: Gitea の Docker イメージの 1.26.2 以前。修正は 1.26.3。1.26.3 のコードページの不具合を直した 1.26.4 への更新が推奨されている。
- **規模の目安**: インターネットに露出した Gitea インスタンスは約 6,200 件（外部の観測）。

### 時系列

- **（事前）**: Gitea の公式 Docker イメージが、`REVERSE_PROXY_TRUSTED_PROXIES = *` を既定にしていた。
- **2026-06-20**: Gitea 1.26.3 が公開され、CVE-2026-20896 を含む複数のセキュリティ修正が提供された。リバースプロキシ認証を明示的に有効にする方式に改め、既定の `*` を外した。
- **2026-06-21**: 1.26.3 のコードページの不具合を直した 1.26.4 が公開された。Gitea は 1.26.4 への直接の更新を強く推奨した。
- **2026-07 上旬**: Sysdig が、開示 13 日後に実環境で初回の悪用の試みを検出したと報告した。初期の調査の段階で、悪用や攻撃の進展には至っていないとされる。

> 技術的な事実は、Gitea の公式のリリースの告知（1.26.3／1.26.4）と NVD の登録に拠る。「開示の時点で実環境で悪用」とする二次報道もあるが、一次に近い Sysdig の観測は「開示 13 日後の初期の調査」で、本 Brief はこの精度で記述した。最新の一次情報を参照されたい。公表されていないことは、対策が無かったことを意味しない。

### 公表後の対応

- **Gitea（go-gitea）**: 1.26.3 で CVE-2026-20896 を修正し、リバースプロキシ認証を、管理者が意図して有効にする方式に変えた。既定の `*` を外した。1.26.4 への直接の更新を強く推奨した。同じリリースで、SSRF（CVE-2026-22874）など複数のセキュリティ修正も提供された。
- **NVD**: CVE-2026-20896 を登録した。
- **Sysdig**: 開示 13 日後に実環境で初回の探索を検出し、初期の調査の段階で、攻撃の進展には至っていないと報告した。
- **運用者への推奨**: リバースプロキシの後ろで ID のヘッダーを使う構成では、リバースプロキシがヘッダーを確実に上書き・除去し、Gitea が信頼する送信元を最小にすることが、緊急の対応として共有された。露出したインスタンスの即時の更新も推奨されている。
