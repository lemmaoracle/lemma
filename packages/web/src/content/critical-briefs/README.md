### タイトル

実際の Brief がそろって守っているのに、ここに書かれていなかった規則（2026-09-12
に直近11本を数えて確認）。

- **`—` の前半に、検索の取っ掛かりになる固有名を前方から置く**（製品名・組織名・
  脆弱性名・コードネーム）。ランキングや一覧は前半しか出さないので、ここに固有名が
  無いと引けない。11本中10本がこの形。
  例: `x402 決済のファシリテーター 15 社すべてで…` / `ServiceNow AI Platform で、…`
- 固有名を頭に立てたいときは **`名前：` のコロン形**も使う。
  例: `IDScan.net：本人確認のために窓口へ渡した…`
- **出典・識別子は前半の末尾に丸括弧で**置く。
  例: `…10時間未満で侵害した(Unit 42調査)` / `…機能していた(CVE-2026-59822、CISAが実悪用を確認しKEV登録)`
- H1 は**平叙文**（「〜した／〜された」）。体言止めにしない。
- 後半（`—` の後ろ）は**何が構造的に欠けていたか**を1文で。
  例: `— 支払いの検証と決済の確定が、行動の前に結び付いていない`
- **表紙の `key_figures` に出す数字（件数・人数・金額）はタイトルに入れない**（2026-10-22・153 から）。
  記事では H1 のすぐ下の表紙に大きく出て、一覧と共有カードには `og_lead`・`impact`・`og_headline` が出す。
  タイトルは何が起きたかと何が欠けていたかに絞る。既存の Brief は改訂のついでに外す。
- `title_en` も同じ原則。

### 検索結果の題名と説明（`search_title` / `search_description`・日本語・任意）

H1 の長い一文は、検索結果では頭の 30 字ほどしか見えない。検索する人は事件の名前で調べ
（「〇〇 不正アクセス」「〇〇 委託先 どこ」「〇〇 安全」・Search Console・2026-10-25）、
何が起きたかを知りたいので、`<title>` と meta description にだけ別の文を出せる。表紙の
見出し・OG・一覧は変わらない。

- `search_title`（32 字まで）：**会社名・サービス名＋事象**を先に。後ろに「経緯」「手口と対策」など、
  ページで分かること。H1 と違い、件数・金額を入れてよい（検索で見分けやすい）。
  例: `阿波銀行の不正アクセス：2万7,745件漏えいの経緯` / `ZUU のニセ社長詐欺：チャットの指示で9,600万円送金`
- `search_description`（120 字まで）：何が起きたかを 1 文（出典を丸括弧で）＋「何が起きたか、なぜ〜か、対策を整理。」
- 事実は本文と同じ言い方・同じ数字。落ち度の断定や「防げた」は書かない。外国の通貨は円の目安に「相当」を付ける。
- 事件名で探されている Brief から足す（Search Console の検索語を見る）。

### 国内の事案は早く出す（2026-10-25）

事件の名前での検索は、会社の公表の直後に集中する。国内の大きな事案（不正アクセス・情報漏えい・
送金の詐欺など）は、**公表から 3 日以内に初版**を出し、`search_title` / `search_description` も初版から付ける。
続報（第 N 報）で経路・件数・原因が出たら改訂する（攻撃・侵入経路は未公表なら未公表と書いて出し、判明したら直す）。
早く出しても、一次の公表に拠る・断定しない・落ち度を書かない、は変えない。X の国内の比率（直近 3 本に 1 本まで）は
出し方の決まりで、Brief を早く出すこととは別。

### 下書きと公開（2026-10-26）

新しい Brief は `status: draft` で書き、下書きのまま PR を出してマージする。下書き（`published` 以外）は
本番に出ない。出るのは Cloudflare Pages の main 以外のブランチのプレビューと、手元の dev
（`LEMMA_SHOW_DRAFTS=1` を付けたビルド）だけ（`lib/briefDrafts.ts`）。プレビューでは記事のパンくずに
「下書き」のラベルが付く。

1. 下書きで PR を出し、ビルドとプレビューで見た目を確認してマージする。
2. main に入ると prerelease ブランチが main と同じになる（`.github/workflows/sync-prerelease.yml`）。
   回覧はリンク 1 本：<https://prerelease.web-zgj.pages.dev/ja/critical/drafts/>
3. 承認は CLUBS のいつもの仕事「Critical Brief 作成ルール」の承認ポイントで、回ごとに 1 回にまとめる。
   直しのある Brief は外して次の回に回す。
4. 承認された Brief を `status: published` にする PR を出し、マージすると本番に出る。
   frontmatter の `published`（公開日）も本番に出す日に直す。

国内の大きな事案を 3 日以内に出す決まり（上）は、承認までを含めて 3 日で数える。

## 6章構成

見出しは**番号付き**で書く。目次（§1〜§6）と本文はこの番号で揃う。

| 章 | JA 見出し | EN 見出し | 役割 |
|---|---|---|---|
| §1 | `## 1. TL;DR` | `## 1. TL;DR` | 結論。落差を文章として溶かす |
| §2 | `## 2. 何が起きたか` | `## 2. What happened` | 概要 bullet＋攻撃の連鎖（番号付き） |
| §3 | `## 3. 時系列 — 公表と対応` | `## 3. Timeline — disclosure and response` | 開示・パッチ・業界反応 |
| §4 | `## 4. なぜ止まらなかったか` | `## 4. Why it wasn't stopped` | 構造的論点。✓検出は効いた／✕証明が無かった を本文で |
| §5 | `## 5. 証明があれば、何が変わるか` | `## 5. What proof would have changed` | 処方（report レイアウトでは `## 5. 対策するには` / `## 5. How to counter this`） |
| §6 | `## 6. Sources` | `## 6. Sources` | 一次ソース |

**「検出と証明の落差」は独立章にしない。** §4 と §5 の骨格そのものにする
（落差の要約は TL;DR の結びが担う。旧 gap_* パネルは退役）。「検出と証明の落差」
「構造的」はブランド語なので、章名から消えても**本文の語彙としては使い続ける**。

### §1 TL;DR

- **数文で短く**。詳細は §2 以降に押し出す。検索語（製品名・事案名）を前方に。
  末尾の「§1…§8 参照」のような番号羅列は禁止。
- 結びは **「効かなかったのは、…する層である。」で断ち切る**。
  「検出と事前証明は代替でなく補完である」の定型文は **TL;DR に入れない**
  （補完のポジショニングは §4・§5 が担う）。
- 型: 「検出は効いていた。効かなかったのは、◯◯を独立に確かめる層である。」
  の対比を太字で立てるとよい（047 参照）。

### §2 何が起きたか

- 事実のみ。**概要 bullet**（被害規模・主体・調査方法・公式情報など）→
  接続文（「攻撃は次の連鎖で成立している。」等）→ **連鎖の番号付きリスト**。
- 「核心」「根本原因」の digest bullet は書かない（§4 の冒頭文が担う。重複する）。

### §3 時系列 — 公表と対応

- 順序: タイムライン ul → 注記 blockquote（一次ソースの限定・研究環境である旨
  など）→ 「公表後の対応と業界の動きは次のとおり。」→ 対応・業界動向 bullet。
- **見出しに「時系列」（EN: Timeline）を必ず含める** — 直後の ul が
  縦線＋ライム縁ドットのタイムライン装飾になるトリガー。

### §4 なぜ止まらなかったか — 圧縮の律

- **連結でなく圧縮**。短い段落 3〜4 本＋引用ブロックが目安。
- 冒頭は結論の一文:
  「この事案の失敗は、◯◯でも◯◯でもない。**…を独立に確かめる層が無かった**ことにある。」
- 続けて「検出は効いていた。…効かなかったのは、その手前である。」を
  **1段落に畳む**（検出の成功列挙と限界の言い直しを重複させない）。
- **カテゴリ帳簿文を書かない**: 「本事案は Pillar NN の `X` カテゴリに属する」
  「secondary に `Y` を併記する」の類い。ヒーローのタグが同じ情報を持つ。
- 印象的な引用（当事者・研究者の言）は blockquote に逃がす。
- 関連 Brief への接続は 1 段落に圧縮する。

### §5 証明があれば、何が変わるか

- 処方の段落（事前証明が経路のどこに 1 段挟まるか）→ Lemma の設計 bullet
  （行動前の認可証明・来歴バインド・スコープ・選択的開示など事案に合う軸）→
  検出との相補で締める。「代替ではなく補完」はここで書く。

### §6 Sources

- **一次ソース優先**。GitHub リポジトリ／README／公式 statement は直読
  （`gh api` 等）してから書く。二次報道はリスト・CVE 帰属・件数・削除状態を
  誤ることがある。URL は 200 を確認。各行に（一次）（独立解析）等の位置づけを添える。

## report レイアウト（opt-in・2026-10）

frontmatter に `layout: "report"` を書いた Brief だけが、レポート型の面で描画される
（見本: 032）。書かない Brief はこれまでどおりの面のまま。6章構成と上の各章の規則は
そのまま守る。

**オンになるもの**: スレートの表紙（`brief_no` を種にした生成グラフィック＋
`key_figures`）、表紙下のメタ行（事案日／公開／改訂／発行）、「01 見出し」形式の
章見出し、目次だけの右レール（脅威バナー・ブランド面は出ない）、下の部品 CSS。
冒頭の改訂注記 blockquote は描画されず、版と日付はメタ行に出る（md には残す——
dateModified がここから読む）。「参照: 」はカードにならず1行のまま。

**§3 は接続文（「公表後の対応と業界の動きは次のとおり。」）の代わりに
`### 公表後の対応` の小見出しを置いてよい。**

**§5 の見出しは `## 5. 対策するには`**（EN: `## 5. How to counter this`）。読者が自社で
何をすればよいかを書く章で、製品の処方ではない。

### proof の章立て（opt-in・2026-10-31・165 から）

frontmatter に `sections: "proof"` を書いた report の Brief は、事実の章を後ろに回し、
「何が正しい操作として通ったか」と「何を照合すれば区別できるか」を前に置く。一般の攻撃解説
（何が起きた→経緯→原因→対策）と同じ並びにしないため。書かない Brief は上の章立てのまま。

| 章 | 見出し（JA / EN） | 書くこと |
|---|---|---|
| 01 | 要点 / Summary | 1段落。表紙に無いことだけ（数字と社名を繰り返さない）。太字は、経路を問わず言える一般論の1文 |
| 02 | 通った操作 / What got through | `- **ラベル**: 本文`。通った操作／受け付けた側に届くもの（一般論は「一般に」、当事者の見立ては帰属つき）／公表されていないこと |
| 03 | 何を照合すれば区別できるか / What would tell them apart | 冒頭に区別できる条件を1文 → 帯（`insight.quote`）→ 誰が出すか／どこで照合するか／何が残るか → 図表（証明の層は「公表からは分からない」）→ 落差の1文と関連 Brief |
| 04 | Lemma でできること / What Lemma does | リード（Lemma が何を照合するか。検出ではない）→ 注意したい業界・業務 → 表「いまの対策と Lemma の違い」→ 1段落 → 注 → 点検チェックリスト |
| 05 | 事実と時系列 / Facts and timeline | 事実の表（サービス・確認されたこと・情報・影響・脅迫など標準のラベル）→ `### 時系列` → 注の blockquote → `### 公表後の対応` |
| 06 | Sources | 上と同じ |

- **題名**は「社名：何が起きたか」だけ。` — ` の後半（欠けていた層）は付けない。表紙は、題名＝何が起きたか、
  `key_figures`＝大きさ、`self_check`＝読者が最初にすること、と役目を分ける。`self_check` と同じ問いを
  チェックリストに置かない。
- **04 の表**は、操作の種類ごとに列を分け（例：出金・出金先の変更／範囲を超える注文／範囲の内の注文）、
  どの列にも状態語（効かない／一部／関係しない／効く）を書く。Lemma が効かない列も同じ表に出す。
  表の下の注には、働く条件（どこに照合を組み込むか、鍵をどこに置くか）、通ってしまう場面、
  「表は何を照合しているかの比較で、今回の事案で止まったかを示すものではない」「侵入を検出・防止するものではない」を書く。
- **言い過ぎない**：「Lemma なら防げた」と書かない。公表されていないことを「無かった」と書かない
  （「公表からは見えない／分からない」は 1 本に 1 回まで、太字にしない）。公表されていない因果
  （盗まれた情報→不正な取引など）を前提にしない。05 の注に「公表されていないことは、対策が無かったことを意味しない」を置く。
- **帯（`insight.quote`）**は、核心を言い切る一般論の1文（「別々の事実である」型の言い回しにしない）。
- **`gate`**（内部の値・記事に出さない）：当たる Proof Gate のゲート。`payment-instruction` / `account-change` /
  `signing` / `delivery` / `disclosure` / `identity` / `intake` / `agent-operation` / `permission-change` / `none`。
  Proof Gate の名前は、製品のページがサイトに出るまで記事に書かない。
- 表紙のボタンは「Lemma でできることを見る」になり、04 へ飛ぶ。セルフチェックの項目は 04 のチェックリストから取る。

### 重ねて言わない（2026-10-21・069 から）

- **§1 の 3 段落目**は「（気づいていたが）◯日に◯◯は通った。効かなかったのは…層である。」の
  2 文。§4 で検出の経緯を言い直さない。
- **§4** は「冒頭の結論 2 文 → 図表 2 → 検出が働いた範囲と落差（3 文まで）→ 関連 Brief 1 文」。
  関連 Brief は事案名と一言の括弧書きで足りる（下にカードが出る）。
- **§5** の業界・業務の説明に書いた「なぜ同じ穴があるか」を、表の後で段落にして繰り返さない。
  対策の表は 4 行まで。状態語は中立に並べ、Lemma で埋まる行だけを色で目立たせることはしない。
- **時系列**は日付だけのラベル（時刻・範囲は本文側）。検知から封じ込めまでの空白は、
  公表された日時でたどれるときだけ書く（推定の間隔を描かない）。

### 自社で確かめる（frontmatter・任意）

```yaml
self_check: "導入したアプリと、それぞれに与えた権限を把握しているか。"  # 読者への問い1文
```

表紙のメタ行の下・TL;DR の上に、アイコンつきのカード（問い＋「対策を見る」ボタン＝§5 へ）で出る。
`self_check` が無ければカードごと出ない。

- 「〜か。」の問いにする（答えが「いいえ」になりやすい問いほど、続きを読む理由になる）。
- 製品名・画面名は入れない。事案を知らない読者が自社に置き換えられる言い方にする
  （具体的な手順は §5 が持つ）。
- 被害の後ではなく、手前の段を問う（2026-10-22・069 から）。「漏れたら何を言えるか」「作られたら気づけるか」
  のような後の段の問いは、§5 の点検チェックリストに置く。同じ問いがチェックリストにあれば、そちらを差し替えて重ねない。
  「送金の前に」「返す前に」止められるかを問う文は、被害の前を問うのでそのままでよい（032・110）。
- 二重チェック（「作業者以外が確かめられるか」）ではなく、仕組みを短く問う。「照らす」でなく「照合」。

### 出典の折りたたみ

§6 の種別に「一次」（EN: Primary）を含む行は開いたまま、それ以外（報道・解析）は
「報道・解析 N 件」の開閉にまとめて出る（番号は続き番号）。一次ソースは減らさない。

```yaml
  - { value: "05-23 → 05-28", label: "…" }

  label: "ログインだけで確定する操作"
```

### 一覧の索引（2026-10・レイアウトを問わず書ける）

一覧（`/critical/briefs/`）は「いま読む 3 本 → 対策から読む → そのほかの新着」で組む。
各 Brief の frontmatter に次を書くと一覧に出る。`attack_method` / `operations` / `controls` は、
記事の「似た事例を一覧で読む」（下）にも使う。

（`primary_category`）は内部分類として残し、一覧の入口には使わない。

`countries` だけは記事にも出す（表紙の下の段の「国・地域」）。一覧では行の先頭のラベルと
「国・地域」の絞り込みになる。選ぶのは**事案が起きた国**（被害を受けた組織の所在、公表・
処分した当局の国）で、調査した研究者の国ではない。OSS・ライブラリの脆弱性、暗号資産の
プロトコル、AI のツールや模型の研究、多国にまたがる攻撃は `global`（国際）。語彙は
`config/briefFacets.ts` の `BRIEF_COUNTRIES`。lemma_oracle の X 投稿でも、書き出しの
ラベルに国を入れる（`A spoofing case in the UK:`）。

`industries` / `operations` / `controls` はチップとしては記事に描画しない。語彙・ラベル・
アイコンは `config/briefFacets.ts`。

**似た事例を一覧で読む（2026-10-24）**：記事に、似た事例の一覧（アーカイブの絞り込み）への
入口をテンプレートが出す（`components/BriefNextRead.astro`・選び方は `lib/briefNextRead.ts`）。
対策を探して来た人が、記事を 1 本読んで帰らずに、似た事例へ移れるようにするため。
- 主役：手口（`attack_method`）と業務（`operations`）のうち、付いている Brief がいちばん
  少ない＝この記事にいちばん近い分類（158 なら「振込先・口座の変更」）。
- 対策：主役で絞った事例のうち、この記事の対策（`controls`）も付いているもの。主役と同じ
  件数になるものは出さない。
- 置き場所：2 章（何が起きたか）のあとの 1 行、5 章（対策するには）のあとのブロック、
  広い画面では右レールの目次の下（ブロックが見えている間は隠す）。
md には何も書かない。`controls` は §5 の「必要なこと」と同じ順に書く（「記録する」は最後に
回る）。分類の無い Brief は、末尾に従来の関連 Brief が出る。

**記事の入口（2026-10-24）**：TL;DR のあとに 1 行、§5 のチェックリスト（とその「注：」）
のあとに帯で、入口を出す（`components/BriefWeeklyCta.astro`・行き先は `config/cta.ts`
の、英語は `BRIEF_TLDR_CTA_URL` / `BRIEF_CHECKLIST_CTA_URL`・`ref` で置き場所を分ける。日本語は記事の `operations`
から `selfCheckPageFor` で訴求ごとのページを選ぶ・`payment-change` の記事は不正送金のページへ、当たるページが無い記事はメールの相談が主になる・2026-10-25）。日本語は
セルフチェック（`/ja/critical/self-check/?from=<slug>`：全 report の点検チェックリストを場面ごとに
まとめ、担当（経理など）を選ぶと場面がまとめて選ばれ、お急ぎ点検かじっくり点検かを選んで、画面で はい／いいえ／分からない で答える・会社や個人は分からない形で、どの項目にどう答えたかだけを GA4 で集計する（リサーチ用）・不安な人は結果から
メールで相談（Tally 2jE9dj））、英語は定期のメールの登録。点検表を Excel で配ると一気に出回るので、
ファイルは渡さない。チェックリストの箇条はセルフチェックのチェック項目になるので、1 項目 1 文で、はい／いいえで答えられる形に書く（「〜ていないか」は避け、「はい＝できている」と読める形に）。事例をまたいで同じ項目は `data/selfCheckItems.ts` で 1 項目にまとめる（元の項目を「Brief 番号-順番」で並べる）。そこに無い新しい項目は記事の文のまま 1 問として出るので、新しい Brief を出したら、既存の項目と重なるかを見てまとめ直す。本文は登録の先に置かず、表も畳まずに全部読めるままにする
（検索から対策を探しに来た人を答えの手前で止めないため。畳んでも SEO は変わらず、読み手に
とっては表も答えの一部）。

記事中の「注意したい業界・業務」は md 側で説明文つきの表として書く。EN ファイルの `key_figures` /
`glossary` / `insight` は英語で書く。

- **§1 の行ラベル**は frontmatter `summary_labels: ["…", "…", "…"]` で変えられる。
  省略時は「何が起きたか／なぜ見分けられないか／欠けていた層」。段落の数と
  ラベルの数が違うと組み替えず、段落のまま出る。
- **太字の後の空白**: 日本語で `**…。**本文` と続けると強調が閉じない（下の
  「Markdown の落とし穴」）。`**…。** 本文` と空白を1つ挟んで書けば、全角の
  句読点・括弧で終わる強調の直後の空白は描画で落ちる。
- **出典**: 種別は太字の末尾の（）。題の末尾の（日付）は付記の頭に「日付 · 」で出る。
  区切りは最後の ` — `。`<https://…>` の自動リンクは `https://`・`www.`・末尾の `/`・
  `.html` を落として表示し、長い URL は `host/最初の段/…` に縮める。表示を決めたい
  ときは `[表示](URL)` で書く。英語の題（引用符で始まる題）の前には空白が入る。
- **引用符**: markdown の `"` `'` は描画で “ ” ’ になる（サイト全体の smartypants）。

HTML ブロックの中に**空行を入れない**（空行で markdown に戻る）。図表番号も手で書く。


図表 1 の段は 3〜5。列は段の数で等分され、1行に並ぶ（4段に収めるために段を畳まない）。

図表 2 の落差（`rx-gap`）の型は 032 を写す。上の表の部品も、形に収まらないときは
これまでどおり HTML で書いてよい（書いた HTML はそのまま通る）。

### 書かないもの

- **分析の本文に製品名・CTA を書かない。** 末尾 CTA はテンプレートが出す。
- **ファセットのチップや「この対策で探す」の行を md に書かない。** 同じ手口・対策への
  入口は、テンプレートの「似た事例を一覧で読む」が出す。

## 記事末尾の定型

```markdown
## 6. Sources

- ...

参照: [「AI 時代のサイバー防衛に残された、最後の層」](https://lemma.frame00.com/ja/blog/detection-is-not-proof/)、[Pillar 02 — 検証可能 AI](https://lemma.frame00.com/ja/pillars/#inference)、[Trust402](https://lemma.frame00.com/ja/trust402/)
```

- **参照カード**: 「参照: 」（EN: `References: `）で始まる段落を Sources の後に
  置くと、**リンクだけ**が抽出されて記事末尾のカード列になる（地の文はページに
  出ない）。BLOG / PILLAR / PRODUCT のラベルは URL から自動判定。事案に関係する
  リンクだけを入れる（無理に4枚並べない）。
- **配布定型文（旧 §9）は書かない** — テンプレートが Sources の後に描画する。
  係争中の免責など**個体差のある注記だけ** md に書く（077 参照）。
- **改訂履歴**: `version` を上げるとテンプレートが描画。改訂注記の blockquote は
  本文冒頭（`## 1.` の前）に置いてよい（077 参照）。

## リンク規約

- 本文中の「Brief NNN」は**必ずテキストリンク**にする:
  JA は絶対 URL `https://lemma.frame00.com/ja/critical/briefs/<slug>/`、
  EN は相対 `/critical/briefs/<slug>/`。
- blog / pillars / 製品ページも同様（JA=`/ja/...` 絶対、EN=相対）。

## Markdown の落とし穴

- **「」『』（）に隣接する強調は壊れる**: `な**失敗…」**であり` は CommonMark の
  flanking 規則で `**` が素のまま露出する。括弧で始まる・終わる強調スパンは
  `<strong>…</strong>` を使う。
- 表は白カード・コードブロックはスレートのグラデで描画される（装飾は
  テンプレート任せ。Shiki テーマ指定などは書かない）。
- 見出し直前の `hr`（`---` の直後に `##`）は自動で非表示になるので気にしなくてよい。
- `/api/v1/**` のようなグロブ表記はインラインコード（バッククォート）に入れる。

### セルフチェックのチェック項目の言葉

チェックリストの箇条はセルフチェックで経理・経営・情シス・総務の人が読むので、`data/selfCheckItems.ts` にまとめるときは、リポジトリ直下の `DESIGN.md` の「Lemma の言葉」に沿って言い換える（人がする手順は「確認」・「照合」は Lemma の機能だけ など）。記事本文（§4・§5 や frontmatter の `self_check`）の「照合」は、仕組みを問う言葉なのでそのままでよい。
