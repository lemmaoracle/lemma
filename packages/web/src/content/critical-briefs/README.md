## 1. 進め方

### 1.1 選ぶ

**主軸**（2026-10-01 本人決定・スカウト射程の見直し。関心が開発サプライチェーンから業務ワークフロー事故へ移ったため）

- 主軸は、**送付・公開・承認・支払が、実行の前に中身・宛先・権限を照合されずに通った業務ワークフロー事故**。
  AI の事案と人手の事故（誤送付・誤公開・誤承認など）を同格に扱う。
- 開発サプライチェーン系は、被害規模が大きいか業務への波及が明確な大型事案だけ（例：Brevo 侵害で最大 10 万サイト）。
  研究段階の脆弱性やパッケージ単位の事案は見送る。
- 製品発表など事案でない業界の動きは Brief にせず、スカウト結果の末尾にブログ／ポジショニングの素材として別枠で挙げる
  （例：NVIDIA のエージェント封じ込め基盤は、実行時の封じ込めと Lemma の実行前の認可証明の違いを書くブログの題材に回す）。
- **フロンティアラボ内部の評価・研究エージェントの逸脱は対象から外す**。Brief 144・110 は外し、148・132・129 は
  一般企業の統制の話に書き換えて維持する（2026-10-16 本人承認）。

**寄せ方**

- 事例探しは、**直近 10 本に海外を 6 本以上**入れる。請求書 PDF の口座書き換え・取引先メールの乗っ取り・誤送付・
  医療と製造を重点に探す。日本の比率は X の決まり（[1.6](#16-出したあと)：国内は直近 3 本に 1 本まで）に従う。
  Brief を書く順にも海外の事案を混ぜる（2026-10-23 本人）。
- 送金系の次に探す型（まだ無い型）：国内中小企業の LINE グループを使う CEO 詐欺（警察・IPA の公表から）、
  請求書 PDF の口座の書き換え、取引先側のメールが乗っ取られた事例。対策の章は「新しい振込先や送金の理由を、
  登録済みの連絡先や裏付けと照合してから払う」形で書く。
- **薄いところから探す**：gate・対策・業界の本数を数え、薄いものから事例を探す。型ごとに担当を分けて並行に探し、
  一次資料を開いて確かめたものだけを候補にする。検索は題名で引かれるので、同じ型でも組織が違えば別の Brief にする。
  型ごとに 2 本ずつ下書きで書いて回覧する。
- 候補の調査は、取得・探索・検証・採点・出力に分けて進める（候補ごとに何を根拠に落としたかが残る）。

**実名の二層基準**（2026-08-07・草稿 125〜127 のレビューで合意）

- 実名で摘示する事案は一次ソースを必須とする。一次が無いなら実名を出さない（公開保留と実名記載は両立しない）。
- 構造・手口の分析は、骨格が一次で立てば可。細目はベンダーの独立解析に帰属を明示し、どこまでが一次かを
  05 の注（旧い型では §3 の注記）で示す。
- 企業名は書いてよい（例：メタウォーター）。自治体名は要注意（掲載前に確認）。

### 1.2 ストックと週の回し方

- **Brief 調査は毎週木曜**（CLUBS のくり返すタスク）。
- ストックは、足した日に札（**書く／待つ／見送る**）を付ける。「待つ」には、何が出たら書くかを 1 行書く。
- **月・木**に「書く」を 3 本まで書き、3つの立場のレビュー（[1.4](#14-確かめる)）を通して下書きでマージする。
- **火・金**に本人が「問題なし」を付け、**水・翌週の月**に公開の PR を出す。
- 回覧待ちが 5 本を超えたら、書かずに確認を先にする。
- **国内の大きな事案は早く出す（2026-10-25 本人）**：事件の名前での検索は、会社の公表の直後に集中する。
  国内の大きな事案（不正アクセス・情報漏えい・送金の詐欺など）は週を待たず、**公表の翌日に書き**、
  **公表から 3 日以内に初版**を出す（3 日は承認までを含めて数える）。`search_title` / `search_description`
  （[4.8](#48-検索結果の題名と説明search_title--search_description)）も初版から付ける。
  続報（第 N 報）で経路・件数・原因が出たら改訂する。早く出しても、一次の公表に拠る・断定しない・落ち度を書かない、は変えない。
  X の国内の比率（直近 3 本に 1 本まで）は出し方の決まりで、Brief を早く出すこととは別。

### 1.3 書く（番号・ファイル・JA/EN の対）

- Brief は `<NNN>-<slug>.md`（例：`047-openclaw-agent-phishing.md`）としてここに置き、
  **同名ファイルを `../critical-briefs-en/` にも必ず作る**（JA/EN ミラー・英語は [6](#6-英語版の作り方)）。
  ローダーの glob は `[0-9]*.md` なので、この README は収載されない。
- **番号は詰める**：新しい Brief は**空いている番号のうち最も小さいもの**を使い、空きが無ければ最大＋1 にする
  （ドラフトに書かれた番号は使わない）。
- 取り下げた Brief の URL は `public/_redirects` で一覧へ 301 する。
- URL：`/ja/critical/briefs/<NNN>-<slug>/`（JA）／`/critical/briefs/<NNN>-<slug>/`（EN）
- frontmatter は [4.1 のひな形](#41-ひな形proof)から書く。本文は [2](#2-proof-の章立て) の章立てで書く。
- **攻撃・侵入経路は必ず調べる**（2026-10-17 本人：自社の視点では攻撃経路が一番知りたい）。書き方は
  [2.3](#23-02-通った操作)。公表を待たずに書き、続報で経路が出たら改訂する（026 コミックシーモアから・2026-10-19 本人 OK）。

### 1.4 確かめる

**3つの立場のレビュー**：Brief を書いた・書き直した PR は、書いた AI と別の AI が 3 つの立場で 1 本ずつ見て、
同じ PR で直してからマージする。PR に立場ごとの指摘と直したことを書く。

1. **事実確認**：一次資料と数字・日付・帰属（記録は下の brief-factcheck）。
2. **ルールと読みやすさ**：この README と決まったやり方に合うか・一般の開発者や AI の利用者が読んで分かるか
   （内容の専門性が上がっているので、読みやすさの観点を必ず入れる）。目立つところ（[2.8](#28-表紙と目立つところ)）は必ずここで見る。
3. **英語**：JA と同じ事実か・自然か・人を指す代名詞は they/them。

**公開前の固定チェック**：一次ソースの URL が生きているか（200 を確認）と、日英の frontmatter の整合を毎回確かめる。
ビルドのあと、OG の画像（日英）を目で確かめる（[4.9](#49-og共有カード)）。

**事実確認の記録（2026-11-11）**：事実確認を終えた AI は、不一致と言い過ぎを本文（JA・EN）に直し、
**本文を直してから**、同じ PR で記録を書く。

```sh
node packages/web/scripts/brief-factcheck.mjs <id> --by "Claude Opus 5.5" --pr <番号>   # 英語版は --en
```

- 直す所が無くても記録は書く。CLUBS のノートだけに残さない（回覧の札は記事の記録しか読まない・11/12 に 196〜208 が「まだ」のままだった）。
- 直した中身は 1 行に収まらないので PR の説明かコメントに書き、`--pr` にその PR の番号か、コメントの URL を渡す
  （札の横に「修正の記録：PR #N」のリンクが出る・直しが無ければ省く）。
- frontmatter に `fact_check: { by, at, rev }` が入り、回覧の一覧と記事の下に「AI の事実確認 ✓ Claude Opus 5.5・11/11」が出る。
- あとで本文を直すと「確認のあと変更あり」に変わるので、直したら確認し直して流し直す。
- `--by` はモデル名まで（「Claude」だけは通らない）。

### 1.5 回覧と公開（2026-10-26）

新しい Brief は `status: draft` で書き、下書きのまま PR を出してマージする。下書き（`published` 以外）は本番に出ない。
出るのは Cloudflare Pages の main 以外のブランチのプレビューと、手元の dev（`LEMMA_SHOW_DRAFTS=1` を付けたビルド）だけ
（`lib/briefDrafts.ts`）。プレビューでは記事のパンくずに「下書き」のラベルが付く。

1. 下書きで PR を出し、ビルドとプレビューで見た目を確認し、[1.4](#14-確かめる) を済ませてマージする。
2. main に入ると prerelease ブランチが main と同じになる（`.github/workflows/sync-prerelease.yml`）。
   回覧はリンク 1 本：
   <https://prerelease.web-zgj.pages.dev/ja/critical/drafts/>
3. 承認は下書きごとの「問題なし」（記事の下と一覧のボタン・CLUBS のいつもの仕事「Critical Brief 作成ルール」に名前つきで残る）で行う
   （2026-11-05 から。**承認ポイントは使わない**）。
   「修正したい」が残った Brief は直して PR にし、frontmatter に直した記録を足す：
   ```yaml
   draft_fixed:
     - date: 2026-11-08
       note: "時系列の 09-24〜10-06 の行を 2 行に分けた"   # 何を直したか 1 行（80 字まで）
   ```
   一覧と記事の下に「修正済み」の印が付くので、読み直して「問題なし」を押し直してもらう。
4. 「問題なし」の付いた Brief を `status: published` にする PR を出し、マージすると本番に出る。
   frontmatter の `published`（公開日）も本番に出す日に直し、`draft_fixed` は消す。
5. 回覧のあいだに新しい公表（続報）が出ていないかを確かめる（`key_figures` の数は [2.8](#28-表紙と目立つところ)）。

## 2. proof の章立て

frontmatter に `layout: "report"` と `sections: "proof"` を書く（2026-10-31・165 から）。事実の章を後ろに回し、
「何が正しい操作として通ったか」と「何を照合するか」を前に置く。一般の攻撃解説（何が起きた→経緯→原因→対策）と
同じ並びにしないため。見出しは**番号付き**で書く（`## 1. 要点`）。ページでは「01 要点」の形になる。

### 2.1 章の表

| 章 | 見出し（JA / EN） | 書くこと |
|---|---|---|
| 01 | 要点 / Summary | **3 段落**：何が起きたか（表紙に無いことだけ）／公表で分かったこと・その後／経路を問わず言える一般論の 1 文（太字）。[2.2](#22-01-要点) |
| 02 | 通った操作 / What got through | `- **ラベル**: 本文`。通った操作／受け付けた側に届くもの／公表されていないこと。[2.3](#23-02-通った操作) |
| 03 | 実行前の照合 / Pre-execution check | 区別できる条件の 1 文 → 帯（`insight.quote`）→ 誰が出すか／どこで照合するか／何が残るか → 図表 1 → 落差の 1 文と関連 Brief。[2.4](#24-03-実行前の照合) |
| 04 | Lemma でできること / What Lemma does | リード → 注意したい業界・業務 → 表「いまの対策と Lemma の違い」→ 1 段落 → 注 → 点検チェックリスト。[2.5](#25-04-lemma-でできること) |
| 05 | 事実と時系列 / Facts and timeline | 事実の表 → `### 時系列` → 注の blockquote → `### 公表後の対応`。[2.6](#26-05-事実と時系列) |
| 06 | Sources | 一次ソース。[2.7](#27-06-sources) |

### 2.2 01 要点

- **3 段落で書く**と「何が起きたか／分かったこと／なぜ通ったか」の 3 行の要旨になる（rehype・本人 2026-11-04）。
  1 段落のままでも通るが、3 行の形にそろえる。
- 1 段落目＝何が起きたか（表紙に無いことだけ）、2 段落目＝公表で分かったこと・その後、
  3 段落目＝**経路を問わず言える一般論の 1 文（太字）**。
- 3 段落目の太字（なぜ通ったか）は、**比喩と二重否定を使わない**。「共有の入口」のような言い換えをせず、
  誰が・何を・何と比べなかったかをふだんの言葉で書く。公表されていないことは「〜なければ」「〜とは限らない」の形にする
  （「無かったから」と言い切らない）。太字は帯と同じ文にしない。
- **図表 1 は md では 03 に書くが、ページでは 01 の直後に出る**（rehype が動かす・看板の図を先に）。
- 01 のあとには、相談の入口の代わりに Brief の範囲の注意書き（公表された事実から点検できることを整理したもので、
  個別の被害や手続きの案内ではない）をテンプレートが出す。読者向けの窓口の案内は書かない（2026-11-01）。

### 2.3 02 通った操作

- `- **ラベル**: 本文` の箇条で書く。通った操作／受け付けた側に届くもの（一般論は「一般に」、当事者の見立ては帰属つき）／
  公表されていないこと。
- **攻撃・侵入経路**は公表された範囲（経路・止めたサービス・脆弱性への言及・未公表の点）を書く（旧い型では §2）。
  攻撃経路は再発防止のため非公表が多い（133 本中、種類が書けたのは 80 本）。公表を待たずに書く：
  1. 調べて無ければ「**特定済み・非公表**」「**調査中**」を書き分けて明記する。
  2. 対策は、どの経路でも効くものを書く。
  3. 続報で経路が出たら改訂する。

### 2.4 03 実行前の照合

#### 区別できる条件の1文

03 の冒頭の 1 文（2026-11-27）。何が満たされていれば通してよいかだけを書く。
照合の手段（何の記録と・何とは別に・どの鍵で）は書かない。手段は続く「誰が出すか／どこで照合するか」と帯に書く。
手段まで書くと長くなり、条件ではなくやり方に読める（本人 11/27・208「本人が登録した端末の鍵で照合することである」）。

- JA：「経路を問わず区別できる条件は、〜かどうかである。」の形・65 字まで・「照合」「確かめ」「とは別」「ではなく」「記録」を使わない
- EN："Whatever the route, the condition for telling them apart is whether …"・35 語まで・checked / against / apart from / rather than / record を使わない
- 例：「経路を問わず区別できる条件は、ダウンロードしようとしている人が、そのファイルを担当する人かどうかである。」（218）
- 196 番以降はビルドが検査し、守れないと落ちる（`src/lib/check-brief-condition.mjs`）

#### 帯（`insight.quote`）

- **「実行前のゲート」**で書く：どの操作の前に、何を、何と照合するかを 1 文で言い切り、`insight.stop: true` を付ける
  （例：送金の前に、依頼の新しい口座を、届いたメールではなく仕入先の登録済みの連絡先で照合する。
  小見出しが「実行前のゲート」になる・2026-11-04・184 から）。小見出しが場所、1 文が条件。
- **照合するものを「人」と「条件」で書く**（2026-11-26）。「そのアクセスを、相手と記録と照合する」ではなく、
  「開こうとしている人が、正規の共有相手かどうかを、範囲・期限の記録と照合する」。03 の冒頭と図表 1 も同じ言い方にそろえる。
- 「なぜ通ったか」の一般論は 01 の太字に置き、帯と同じ文にしない。「防ぐ」「止める」は使わない。
- 帯は 1 文に収め、長くなるなら条件節を前に出す（[3.2](#32-文の組み立て)）。
- 「ゲート」の語は製品を特定しないので使ってよいが、個別のゲート名（payment-instruction など）は製品ページが出るまで出さない。
- `stop` の無い Brief の帯は「この事案の核心」のまま（[付録 A](#付録-a-旧い型の決まり)）。proof に移した Brief は、
  改訂のついでに書き直して `stop` を付ける。

#### 誰が出すか／どこで照合するか／何が残るか

`- **誰が記録を出すか**: …` `- **どこで照合するか**: …` `- **何が残るか**: …` の箇条で書く（事実の表になる）。

#### 図表 1「「検知」と「実行の前の照合」の違い」

- 型は手書きの HTML（`rx-gap`・[5.2](#52-まだ手で書く部品)）。照合の側は「公表からは分からない」。
- 読み手になじみの無い「証明」「落差」は図と本文で使わない（[2.9](#29-呼び名と言い過ぎない)）。
- 本文の事実を直したら、図表の段・帯・説明文も日英とも同じ言い方に直す（[3.4](#34-本文を直したら図も)）。

#### 落差の 1 文と関連 Brief

- 図のあとに、検知が働いた範囲と、それでも通ったことを 1 段落で書く（検出の経緯を言い直さない）。
- 関連 Brief は事案名と一言の括弧書きで足りる（下にカードが出る）。Brief へのリンクは [5.5](#55-リンク規約)。

### 2.5 04 Lemma でできること

- **リード**：Lemma が何を照合するか（検出ではない）を太字の 1 文で始める（例：**Lemma は、実行前の照合を、…手順に組み込む。**）。
- **注意したい業界・業務**：`### 注意したい業界・業務` に `- **業界 · 名前**: 説明` の箇条で、説明文つきの表として書く。
  誰向けかはここが持つ。ここに書いた「なぜ同じ穴があるか」を、表の後で段落にして繰り返さない。
- **業務ワークフロー事故の書き方**：AI の判断の正しさや人の操作ミスを防ぐとは書かず、送付物と宛先・公開区分・権限の対応を
  実行の前に照合させる形で書く。Lemma が主張できるのは、データの出所・改ざんの有無と、行動前の認可・属性の証明まで
  （honest claim boundary）。人手の事故は、その工程をシステム化／エージェント化する際の照合として書く。

#### 04 の表（`### いまの対策と Lemma の違い`）

- 操作の種類ごとに列を分け（例：出金・出金先の変更／範囲を超える注文／範囲の内の注文）、どの列にも状態語
  （**効かない／一部／関係しない／効く**）を書く。Lemma が効かない列も同じ表に出す。
- 列に、今回の事案で通った経路ではないものを含めるときは、表の前に、今回の経路がどの列かを一文で書く（2026-11-02・166 から）。
- 対策の表は 4 行まで。状態語は中立に並べ、Lemma で埋まる行だけを色で目立たせることはしない（2026-10-21・069 から）。
- 全部を「一部」にせず、止められなかったものは「効かない」にする（2026-10-24 本人）。
- 推定の状態語は PR に一覧で示す。
- 表の下の注には、働く条件（どこに照合を組み込むか、鍵をどこに置くか）、通ってしまう場面、
  「表は何を照合しているかの比較で、今回の事案で止まったかを示すものではない」「侵入を検出・防止するものではない」を書く。

#### 表に入れる行

- 行は、**実行を止める・絞る対策だけ**にする。謝罪・声明・事後の評価・当局の調査や統計・訴訟や起訴・返金や補償・
  脆弱性の開示は行にしない。
- Lemma はデータを消さず、鍵を失効させず、資金を回収しないので、その列で「効く」にしない。

#### 点検チェックリスト

- `### 点検チェックリスト` ＋（説明の段落：例「振込先の変更について、組織で確かめる 3 項目」）＋箇条で書く。
- 箇条はセルフチェックの項目になる：1 項目 1 文で、はい／いいえで答えられる形に書く
  （「〜ていないか」は避け、「はい＝できている」と読める形に）。言葉は [5.8](#58-記事の入口とセルフチェック)。
- `self_check`（表紙の問い）と同じ問いを置かない。被害の後の段の問い（「漏れたら何を言えるか」「作られたら気づけるか」）はここに置く。
- 表紙のボタン「Lemma でできることを見る」は 04 へ飛ぶ。セルフチェックの項目は 04 のチェックリストから取る。

#### 入口（2026-11-01）

- 本文の中の相談の入口は、04 の表のあとの「導入相談・デモ」の帯 1 本（チェックリストのあとの帯は出さない）。テンプレートが出す。
- 帯では誰向けかを名乗らない（帯に「個人は受けない」とも書かない）。
- Proof Gate の製品ページが出たら、帯の行き先を `gate` のゲートのページにする。

### 2.6 05 事実と時系列

- **事実の表**：`- **ラベル**: 本文` の箇条（サービス・確認されたこと・情報・影響・脅迫など標準のラベル）。
- **`### 時系列`**：`- **日付**: 本文` の箇条。**日付だけのラベル**（時刻・範囲は本文側）。
  検知から封じ込めまでの空白は、公表された日時でたどれるときだけ書く（推定の間隔を描かない）。
- **注の blockquote**：一次ソースの限定を書く。必ず「公表されていないことは、対策が無かったことを意味しない」を置く。
  - 実地の侵害でない研究実証は、その旨を明示し、被害規模を誇張しない。
  - 構造分析の細目をベンダーの独立解析に拠るときは、どこまでが一次かを示す（[1.1](#11-選ぶ) 実名の二層基準）。
- **`### 公表後の対応`**：公表後の対応と業界の動きの箇条（普通の箇条のまま）。

### 2.7 06 Sources

- **一次ソース優先**。GitHub リポジトリ／README／公式 statement は直読（`gh api` 等）してから書く。
  二次報道はリスト・CVE 帰属・件数・削除状態を誤ることがある。
- URL は 200 を確認する。各行に（一次）（独立解析）（報道）等の位置づけを添える。書き方は [5.1](#51-普通の-markdown-から組み立てる部品)・[5.3](#53-出典の折りたたみ)。
- AI 生成が疑われる媒体は出典にしない。
- Sources に無い媒体を新しく持ち出さない（[3.5](#35-出典と言い切り)）。

### 2.8 表紙と目立つところ

**題名**

- **題名は「社名：何が起きたか」だけ**。` — ` の後半（欠けていた層）は付けない
  （旧い型の題名の決まりは [付録 A](#付録-a-旧い型の決まり)）。
- 表紙は、題名＝何が起きたか、`key_figures`＝大きさ、`self_check`＝読者が最初にすること、と役目を分ける。
- 題名に、表紙の `key_figures` に出す数字（件数・人数・金額）を入れない（2026-10-22・153 から）。
  記事では H1 のすぐ下の表紙に大きく出て、一覧と共有カードには `og_lead`・`impact`・`og_headline` が出す。
  既存の Brief は改訂のついでに外す。
- 出典・識別子は題名の末尾に丸括弧で置く（例：`…(京王電鉄の公表)`）。題名は平叙文（「〜した／〜された」）で、体言止めにしない。

**目立つところの書き方（2026-11-26・211〜216 の回覧から）**

1. 帯の 1 文は、照合するものを「人」と「条件」で書く（[2.4](#24-03-実行前の照合)）。
2. 01 の太字は、比喩と二重否定を使わない（[2.2](#22-01-要点)）。
3. **目立つところは、公開の前に表現を見直す**：`insight.label`・`insight.quote`・01 の太字・`takeaway`・`key_figures` の `label`・
   `og_headline`・`self_check`。語の誤用（例：「照らさずに」→「確かめずに」）、一般の開発者に通じない業界の語（例：「部店」）、
   崩れた文を直す。レビューの②（ルールと読みやすさ）で必ず見る。
4. **`key_figures` の「最大」「約」の数は、いつの公表の数かを `label` に書く**（例：11 月 24 日の公表時点）。
   続報で数が変わることが多いので、回覧のあいだに新しい公表が出ていないかも確かめる。

### 2.9 呼び名と言い過ぎない

**呼び名（2026-11-01）**

- Lemma の切り口は、会社の看板・見出しでは「**実行前照合**」、記事の本文と図では読みやすい「**実行の前の照合**」
  （英語はどちらも pre-execution check）。
- 検知（後から気づく）と並べて、その手前に置くものとして書く。検知を否定しない。
- 「証明」「落差」は図と本文で使わない。
- Proof Gate の名前は、製品のページがサイトに出るまで記事に書かない（`gate` は内部の値・[4.6](#46-gate-と対策)）。

**言い過ぎない**

- 「Lemma なら防げた」と書かない。
- 公表されていないことを「無かった」と書かない（「公表からは見えない／分からない」は 1 本に 1 回まで、太字にしない）。
- 公表されていない因果（盗まれた情報→不正な取引など）を前提にしない。
- 05 の注に「公表されていないことは、対策が無かったことを意味しない」を置く。
- 落ち度の断定や「防げた」は、検索用の文（`search_*`）を含めてどこにも書かない。相手を断罪しない。

## 3. 文の書き方

### 3.1 用語・文体

- **である調**。「注：」の書き出し・「求める」などの Brief の言葉は変えない（です・ます、※、「要求」にしない）。
- JP 用語は「ゼロ知識証明」（「零知識証明」不可）。
- 「構造的」「structurally」「by construction」は保持する（ブランド語）。
- 外国の通貨は円の目安に「相当」を付ける。

### 3.2 文の組み立て

- **主語を先に出す**：文は「誰が・何を」を頭に置く。
- **条件は 1 文に 1 つ**。条件が 2 つ以上なら文を分ける。帯（核心の 1 文）だけは 1 文に収め、長くなるなら条件節を前に出す。
- 読点で修飾を重ねない。
- **同じ要の語を 1 文に重ねない**：「照合」「承認」「登録済み」のような要の語は、1 文に 2 回まで。
  3 回になるなら文を分けるか、片方を省く。

### 3.3 業界の言葉と外部の校正案

- 本文は平易に書くが、読者の業界に決まった言葉がある物は、その言葉で呼ぶ
  （中身→コンテンツ・記事、道具→ツール、書いた人→執筆者、送り主→差出人、確認→校閲 など）。
  初出には括弧で短い説明を付ける。評価の語や出典に無い語には広げない。
- 平易さの目安は、一般の開発者や AI の利用者が読んで分かること。
- **外部の AI の校正案は、業界の名詞だけを入れる**（例：シンジケート記事・校閲・クレジット・マストヘッド・執筆者）。
  落ち度の評価語（無校閲・チェック漏れ・不全）、体言止めや【】の題名、章の名前、「実行の前の照合」の呼び名の変更、
  出典に無い語（直接契約・生成AI）は入れない。
- 業界の語は、題名より `search_description` と OG のキッカーに置く。

### 3.4 本文を直したら図も

- 本文の事実を直したら、図表 1・2 の段、帯、説明文を日英とも同じ言い方に直す（158〜161 で 4 件ずれた・2026-10-24 本人）。
- 会社の主張は「〜とする」、戻っていない額は「未回収」、止めていない検出は「気づく」まで、と書く。

### 3.5 出典と言い切り

- **出典が言い切っている事実は、迂回せず直言で書く**：出典（警察・当事者の公表）が言い切っている事実は、
  「来たように見え」「〜ことである」のように迂回せず、直言で書く（仕入先を名乗り・求めた）。
  言い切れないときは、迂回でなく帰属を付ける（警察によれば）。言い切りに変えても、評価の語（装う・惑わされる）には広げない。
- **出典の無い記述は外し、言い過ぎは弱める**：出典の無い統計・論評・過去の事例は外し、旧本文の言い過ぎは弱める。
  Sources に無い媒体を新しく持ち出さず、読んでいない資料は「確認できていない」と書く。
  数字や日付が食い違えば、両方を出どころつきで書く。
- 送った側に落ち度を割り当てる発言と、攻撃の再現手順は載せない。
- 一方の公表に拠る落ち度は、その公表の言い方で書く（断定しない）。

### 4.2 基本の項目

- `og_lead_ja` / `og_lead_en`：og:title の先頭 30〜45 字。検索語を前方に。
- **`gap_*` 3点セットは退役した（2026-08-21）。新しい Brief では書かない。**
  右レールの常設パネル「この Brief の核心」を駆動していたが、TL;DR 末尾と §5 の言い換えで新規情報が無く、

```yaml
  - { value: "05-23 → 05-28", label: "…" }

  - { term: "エクストラネット", desc: "…" }

  slug: "confirmed-by-login-alone"   # slug / label は一覧用。記事には出ない
  label: "ログインだけで確定する操作"
  quote: "…"

```

- `key_figures` の数字は題名に入れない。「最大」「約」の数は、いつの公表の数かを `label` に書く（[2.8](#28-表紙と目立つところ)）。

### 4.5 一覧の索引

一覧（`/critical/briefs/`）は「新着 4 本（公開日順・自動。同じ日は番号の大きい順）→ 注目（ピン 1〜2 本）→ 対策から読む →
そのほかの新着」で組む。各 Brief の frontmatter に次を書くと一覧に出る（レイアウトを問わず書ける・2026-10）。
`attack_method` / `operations` / `controls` は、記事の「似た事例を一覧で読む」（[5.8](#58-記事の入口とセルフチェック)）にも使う。

```yaml
industries: ["public-sector"]          # 業界（config/briefFacets.ts・config/industriesV1.ts の slug）
operations: ["delivery"]               # 業務（config/briefFacets.ts）
controls:                              # 対策（8 つ・4.6）
  - { slug: "ownership-check", item: "…" }
attack_method: "impersonation"         # 手口：account-takeover / impersonation / privilege-abuse / supply-chain / human-error / ai-misuse の6つから1つ
countries: ["jp"]                      # 国・地域（必須・2 つまで）。事案が起きた国。国に結びつかないものは "global"
impact: "36 自治体が配信を停止"          # 影響。数字だけにせず何の数かを書く。公表が無ければ書かない
takeaway: "届いた通知が自治体のものかを、送信元の表示とは別に確かめる手順が無かった。"  # 新着・注目のカードに出す一文（新着は自動で出るので、公開する Brief には必ず書く）
```

- **`countries`** だけは記事にも出す（表紙の下の段の「国・地域」）。一覧では行の先頭のラベルと「国・地域」の絞り込みになる。
  選ぶのは**事案が起きた国**（被害を受けた組織の所在、公表・処分した当局の国）で、調査した研究者の国ではない。
  OSS・ライブラリの脆弱性、暗号資産のプロトコル、AI のツールや模型の研究、多国にまたがる攻撃は `global`（国際）。
  語彙は `config/briefFacets.ts` の `BRIEF_COUNTRIES`。Brief には必ず付ける。X の書き出しのラベルにも国を入れる（[1.6](#16-出したあと)）。
- `industries` / `operations` / `controls` はチップとしては記事に描画しない。語彙・ラベル・アイコンは `config/briefFacets.ts`。
- 「注目」のピンは `config/briefPicks.ts` で、読まれているものや世界的に注目された事案を 1〜2 本だけ選ぶ
  （毎週は変えない。ピンの Brief は新着から外れる）。
- EN ファイルの `impact` / `takeaway` / `controls[].item` は英語で書く。

### 4.6 gate と対策

**`gate`**（内部の値・記事に出さない）：当たる Proof Gate のゲートを 10 個の値から 1 つ。
`payment-instruction` / `account-change` / `signing` / `delivery` / `disclosure` / `identity` / `intake` / `agent-operation` / `permission-change` / `none`。

- 選び方（2026-11-02）：その事案で、実行の前の照合が最も当たる操作を 1 つ（迷うときは、被害が最後に確定した操作）。
- **AI の判定が人の不利益（逮捕・給付の判定・採用の判定など）に直結した型は `agent-operation`**（判定の実行の前に、入力と根拠を照合する）。
- `none` は、規制の動き・研究の解説・製品発表など、実行する操作が無いものだけ。
- JA と EN は同じ値。全 Brief に付けてある。製品側で一覧が変わったら、ここを直し、全 Brief の値を見直す（読者が来る前は、直しても影響しない）。
- Proof Gate の名前は、製品のページがサイトに出るまで画面・記事に書かない。

**対策（`controls`）**：次の 8 つの slug から選び、**`audit-trail` は最後に置く**。04 の「必要なこと」と同じ順に書く。
増やすのは、今ある対策に当てはまらない Brief が 3 本たまったとき。

**対策と Gate の対応（内部・2026-11-02 本人）**：一覧の「対策から読む」は 8 つの対策のままにする。8 つは読者が
「何が欠けていたか」を知るための分類で、Gate（実行する操作の種類）とは 1 対 1 に対応しない。近い対応は次のとおり（内部の目安）。
Proof Gate の製品ページが出たら、「対策から読む」を Gate 名の入口に差し替え、`?control=` は新しい入口へ転送する（段階 3）。

| 対策（`controls` の slug） | 近い Gate |
| --- | --- |
| 送り主や口座が本物か確認する（`ownership-check`） | payment-instruction・account-change・identity |
| 入口で、依頼元の認証・認可を確認する（`verify-entry`） | identity・intake・agent-operation |
| 権限は必要な分だけ渡し、古い鍵は失効させる（`limit-and-revoke`） | permission-change・agent-operation |
| 届いたもの（コード・データ・画像）の出どころを確認する（`check-origin`） | intake |
| 個人情報は、必要な分だけ預かり、持たない形にする（`minimize-data`） | disclosure |
| AI・自動化の動きは、範囲と上限の中に収める（`bound-automation`） | agent-operation |
| 確認できるまで、送金や配信を止める（`hold-unverified`） | どの Gate にも共通する動作（止める） |
| 誰が何を確認したかを記録する（`audit-trail`） | どの Gate にも共通する動作（記録する） |

### 4.7 自社で確かめる（`self_check`）

```yaml
self_check: "導入したアプリと、それぞれに与えた権限を把握しているか。"  # 読者への問い1文
```

表紙のメタ行の下・01 の上に、アイコンつきのカード（問い＋「対策を見る」ボタン）で出る。`self_check` が無ければカードごと出ない。

- 「〜か。」の問いにする（答えが「いいえ」になりやすい問いほど、続きを読む理由になる）。
- 製品名・画面名は入れない。事案を知らない読者が自社に置き換えられる言い方にする（具体的な手順は対策の章が持つ）。
- 被害の後ではなく、**手前の段を問う**（2026-10-22・069 から）。「漏れたら何を言えるか」「作られたら気づけるか」のような
  後の段の問いは、04 の点検チェックリストに置く。同じ問いがチェックリストにあれば、そちらを差し替えて重ねない。
  「送金の前に」「返す前に」止められるかを問う文は、被害の前を問うのでそのままでよい（032・110）。
- 二重チェック（「作業者以外が確かめられるか」）ではなく、仕組みを短く問う。「照らす」でなく「照合」。

### 4.8 検索結果の題名と説明（`search_title` / `search_description`）

日本語のみ・任意。H1 の長い一文は、検索結果では頭の 30 字ほどしか見えない。検索する人は事件の名前で調べ
（「〇〇 不正アクセス」「〇〇 委託先 どこ」「〇〇 安全」・Search Console・2026-10-25）、何が起きたかを知りたいので、
`<title>` と meta description にだけ別の文を出せる。表紙の見出し・OG・一覧は変わらない（PR #1026）。

- `search_title`（32 字まで）：**会社名・サービス名＋事象**を先に。後ろに「経緯」「手口と対策」など、ページで分かること。
  H1 と違い、件数・金額を入れてよい（検索で見分けやすい）。
  例：`阿波銀行の不正アクセス：2万7,745件漏えいの経緯` / `ZUU のニセ社長詐欺：チャットの指示で9,600万円送金`
- `search_description`（120 字まで）：何が起きたかを 1 文（出典を丸括弧で）＋「何が起きたか、なぜ〜か、対策を整理。」
- 事実は本文と同じ言い方・同じ数字。落ち度の断定や「防げた」は書かない。外国の通貨は円の目安に「相当」を付ける。
- 付ける Brief：
  - 日本の事案の Brief には書く（CLUBS のやり方）。国内の大きな事案は初版から付ける（[1.2](#12-ストックと週の回し方)）。
  - 事件名で探されている Brief から足す（Search Console の検索語を見る）。
  - 国内の事案だけでなく、海外の事案でも、日本語の検索語（「asos 詐欺」「sumsub 安全」など）が出ている Brief には付ける（2026-11-02）。

### 4.9 OG（共有カード）

report Brief の OG は脅威タイプ名ではなく事件そのものが主役（表紙と同じ生成グラフィックの地）。og:description は `insight.quote` で始まる。

- `og_kicker_ja/en`：事例の種類（例「サイバー攻撃事例 · アカウント乗っ取り」/ "CYBERATTACK · ACCOUNT TAKEOVER"）。
  ライムの札になるので短い 1 行。英語のラベルは 32 字ほどまで。
- `og_headline_ja/en`：何が起きたかを書く。`\n` で行を分け、被害の大きさを `<accent>…</accent>` でライムの 1 行に。
  - 和文は 1 行 12 字まで（合計 40 字を超えるときは 14 字まで）、英文は 28 字ほどまで。超えると勝手に折り返す（2026-10-23 本人・157 で余計な改行）。
  - 1〜2 字だけが次の行に落ちない区切りにする。
  - 研究や報告なら「〜と報告」のように出どころが分かる形にする。
- ビルドのあと、`dist/og` の JA・EN の PNG を開いて目で確かめる（まとめて直すときは日英の 16 枚を 1 枚に並べる）。

## 5. 部品と markdown

### 5.1 普通の markdown から組み立てる部品

部品の多くは、決まった形の markdown を書けば rehype（`lib/rehype-brief-section-number.mjs`）が 032 と同じ HTML に組み替える。
`layout: "report"` の Brief だけで働き、手書きの HTML ブロックはそのまま通る（二重には組み替わらない）。

| `- **ラベル**: 本文` の箇条 | 事実の表（`rx-facts`） | 02・03・05 | §2 |
| 小見出しより前の `- **日付**: 本文` の箇条 | 時系列の表（`rx-tl`）。日付で始まらないラベルは薄い字（`time.nd`） | 05 | §3 |
| 引用 `> …` | 注（`rx-aside`） | 05 | §3 |
| 冒頭の段落 | リード（`rx-lead`） | 04 | §5 |
| 2 列目以降が 効かない／一部／関係しない／効く の表 | 状態のチップ（`bx-st no/part/na/ok`） | 04 | §5 |
| `### 必要になるもの` ＋番号つきリスト | 対策のパネル（`rx-box`・`ol.num`） | 04 | §5 |
| `### 点検チェックリスト` ＋（段落）＋箇条 | 点検のパネル（`bx-checklist`）。直後の段落は説明文 | 04 | §5 |

| `- **ラベル**: 本文` の箇条 | 定義表（`rx-facts`。持ち主の表など） | 04 | §5 |

- **01 の行ラベル**は frontmatter `summary_labels: ["…", "…", "…"]` で変えられる。省略時は proof では「何が起きたか／分かったこと／なぜ通ったか」、

- **太字の後の空白**：日本語で `**…。**本文` と続けると強調が閉じない（[5.7](#57-markdown-の落とし穴)）。`**…。** 本文` と空白を 1 つ挟んで書けば、
  全角の句読点・括弧で終わる強調の直後の空白は描画で落ちる。
- **出典**：種別は太字の末尾の（）。題の末尾の（日付）は付記の頭に「日付 · 」で出る。区切りは最後の ` — `。
  `<https://…>` の自動リンクは `https://`・`www.`・末尾の `/`・`.html` を落として表示し、長い URL は `host/最初の段/…` に縮める。
  表示を決めたいときは `[表示](URL)` で書く。英語の題（引用符で始まる題）の前には空白が入る。
- **引用符**：markdown の `"` `'` は描画で “ ” ’ になる（サイト全体の smartypants）。
- 03 の見出しのあとで、帯（`insight.quote`）は冒頭の段落の直後に出る。`glossary` は事実の表（proof では 05）の直後に出る。

### 5.2 まだ手で書く部品

HTML ブロックの中に**空行を入れない**（空行で markdown に戻る）。図表番号も手で書く。

```html
<!-- 図表 1: 連鎖（rx-step に crit / good） -->
<figure class="rx-ex">
<div class="rx-ex-h"><span class="rx-ex-no">図表 1</span><span class="rx-ex-t">…</span></div>
<p class="rx-ex-cap">…</p>
<div class="rx-chain"><div class="rx-step crit"><div class="who">第三者</div><div class="no">2</div><b>…</b><p>…</p></div></div>
</figure>
```

- 図表 1 の連鎖（`rx-chain`）の段は 3〜5。列は段の数で等分され、1 行に並ぶ（4 段に収めるために段を畳まない）。
- 検知と照合の図（`rx-gap`）の型は 032 を写す（proof の図表 1 の例は 219）。
- 上の表の部品も、形に収まらないときはこれまでどおり HTML で書いてよい（書いた HTML はそのまま通る）。

### 5.3 出典の折りたたみ

06 の種別に「一次」（EN: Primary）を含む行は開いたまま、それ以外（報道・解析）は「報道・解析 N 件」の開閉にまとめて出る
（番号は続き番号）。一次ソースは減らさない。

### 5.4 記事末尾の定型と改訂履歴

```markdown
## 6. Sources

- ...

参照: [「AI 時代のサイバー防衛に残された、最後の層」](https://lemma.frame00.com/ja/blog/detection-is-not-proof/)、[Pillar 02 — 検証可能 AI](https://lemma.frame00.com/ja/pillars/#inference)、[Trust402](https://lemma.frame00.com/ja/trust402/)
```

- **参照**：「参照: 」（EN: `References: `）で始まる段落を Sources の後に置く。layout の無い Brief では、**リンクだけ**が抽出されて
  記事末尾のカード列になる（地の文はページに出ない）。BLOG / PILLAR / PRODUCT のラベルは URL から自動判定。
  report の Brief ではカードにならず 1 行のまま。事案に関係するリンクだけを入れる（無理に 4 枚並べない）。
- **配布定型文（旧 §9）は書かない** — テンプレートが Sources の後に描画する。係争中の免責など**個体差のある注記だけ** md に書く（077 参照）。
- **改訂履歴**：`version` を上げるとテンプレートが描画。改訂注記の blockquote は本文冒頭（`## 1.` の前）に置いてよい（077 参照）。
  report の Brief では冒頭の改訂注記は描画されず、版と日付は表紙下のメタ行に出る（md には残す——dateModified がここから読む）。

### 5.5 リンク規約

- 本文中の「Brief NNN」・関連 Brief は**必ずテキストリンク**にする：JA は絶対 URL `https://lemma.frame00.com/ja/critical/briefs/<slug>/`、
  EN は相対 `/critical/briefs/<slug>/`。
- blog / pillars / 製品ページも同様（JA=`/ja/...` 絶対、EN=相対）。

### 5.6 書かないもの

- **分析の本文に製品名・CTA を書かない。** 末尾 CTA と相談の入口はテンプレートが出す。
- **ファセットのチップや「この対策で探す」の行を md に書かない。** 同じ手口・対策への入口は、テンプレートの「似た事例を一覧で読む」が出す。
- **カテゴリ帳簿文を書かない**：「本事案は Pillar NN の `X` カテゴリに属する」「secondary に `Y` を併記する」の類い。ヒーローのタグが同じ情報を持つ。
- 「§1…§8 参照」のような章番号の羅列を書かない。

### 5.7 Markdown の落とし穴

- **「」『』（）に隣接する強調は壊れる**：`な**失敗…」**であり` は CommonMark の flanking 規則で `**` が素のまま露出する。
  括弧で始まる・終わる強調スパンは `<strong>…</strong>` を使う（01 の 3 段落目の太字もこの形が多い）。
- 表は白カード・コードブロックはスレートのグラデで描画される（装飾はテンプレート任せ。Shiki テーマ指定などは書かない）。
- 見出し直前の `hr`（`---` の直後に `##`）は自動で非表示になるので気にしなくてよい。
- `/api/v1/**` のようなグロブ表記はインラインコード（バッククォート）に入れる。

### 5.8 記事の入口とセルフチェック

**似た事例を一覧で読む（2026-10-24）**：記事に、似た事例の一覧（アーカイブの絞り込み）への入口をテンプレートが出す
（`components/BriefNextRead.astro`・選び方は `lib/briefNextRead.ts`）。対策を探して来た人が、記事を 1 本読んで帰らずに、似た事例へ移れるようにするため。
md には何も書かない。

- 主役：手口（`attack_method`）と業務（`operations`）のうち、付いている Brief がいちばん少ない＝この記事にいちばん近い分類（158 なら「振込先・口座の変更」）。
- 対策：主役で絞った事例のうち、この記事の対策（`controls`）も付いているもの。主役と同じ件数になるものは出さない。
- 置き場所：2 章のあと（3 章の見出しの直前）の 1 行、Sources の直前のブロック、広い画面では右レールの目次の下
  （ブロックが見えている間は隠す）。proof では 02 通った操作のあとと 05 のあと、旧い report では 2 章（何が起きたか）のあとと
  5 章（対策するには）のあと（`markNextReadSlot`）。
- `controls` は対策の章の「必要なこと」と同じ順に書く（「記録する」は最後に回る）。分類の無い Brief は、末尾に従来の関連 Brief が出る。

**記事の入口（2026-10-24）**：要点（TL;DR）のあとに 1 行、チェックリスト（とその「注：」）のあとに帯で、入口を出す
（`components/BriefWeeklyCta.astro`・行き先は `config/cta.ts` の、英語は `BRIEF_TLDR_CTA_URL` / `BRIEF_CHECKLIST_CTA_URL`・`ref` で置き場所を分ける。
日本語は記事の `operations` から `selfCheckPageFor` で訴求ごとのページを選ぶ・`payment-change` の記事は不正送金のページへ、
当たるページが無い記事はメールの相談が主になる・2026-10-25）。proof の記事は [2.2](#22-01-要点)・[2.5](#25-04-lemma-でできること) の置き方（2026-11-01）になる。

- 日本語はセルフチェック（`/ja/critical/self-check/?from=<slug>`）：全 report の点検チェックリストを場面ごとにまとめ、
  担当（経理など）を選ぶと場面がまとめて選ばれ、お急ぎ点検かじっくり点検かを選んで、画面で はい／いいえ／分からない で答える。
  会社や個人は分からない形で、どの項目にどう答えたかだけを GA4 で集計する（リサーチ用）。不安な人は結果からメールで相談（Tally 2jE9dj）。
  英語は定期のメールの登録。
- 点検表を Excel で配ると一気に出回るので、ファイルは渡さない。
- 本文は登録の先に置かず、表も畳まずに全部読めるままにする（検索から対策を探しに来た人を答えの手前で止めないため。
  畳んでも SEO は変わらず、読み手にとっては表も答えの一部）。
- 事例をまたいで同じ項目は `data/selfCheckItems.ts` で 1 項目にまとめる（元の項目を「Brief 番号-順番」で並べる）。
  そこに無い新しい項目は記事の文のまま 1 問として出るので、新しい Brief を出したら、既存の項目と重なるかを見てまとめ直す。

**セルフチェックのチェック項目の言葉**：チェックリストの箇条はセルフチェックで経理・経営・情シス・総務の人が読むので、
`data/selfCheckItems.ts` にまとめるときは、リポジトリ直下の `DESIGN.md` の「Lemma の言葉」に沿って言い換える
（人がする手順は「確認」・「照合」は Lemma の機能だけ など）。記事本文（対策の章や frontmatter の `self_check`）の「照合」は、
仕組みを問う言葉なのでそのままでよい。

## 6. 英語版の作り方

- 章立て・条項は JA と同一。見出しは [2.1](#21-章の表) の対応表どおり（旧い型は付録 A の表）。
- 要点（旧い型の TL;DR）は 1:1 翻訳せず condense する（EN は JA より短くてよい）。
- 事実は JA と同じ。自然な英語にし、人を指す代名詞は they/them（[1.4](#14-確かめる) の③）。
- 区別できる条件の 1 文の英語の形は [2.4](#24-03-実行前の照合)。
- `og_lead_*` は EN ファイルでは英語で書く（両ファイルの frontmatter は title / title_en 等を共有しつつ、og_lead_* は各ロケールの言語）。
- EN ファイルの `key_figures` / `glossary` / `insight` / `impact` / `takeaway` / `controls[].item` は英語で書く。
  `gate`・`controls` の slug・`attack_method`・`countries` は JA と同じ値。
- OG の英語：キッカーは 32 字ほど、見出しは 1 行 28 字ほどまで（[4.9](#49-og共有カード)）。
- 事実確認の記録は `--en` を付けて英語版にも流す（[1.4](#14-確かめる)）。

## 付録 A 旧い型の決まり

layout の無い Brief（59 本）と、`layout: "report"` だけで `sections: "proof"` の無い Brief の決まり。新しくは書かない。
旧い Brief を直すときだけ使う。直すついでに proof に移すなら [付録 B](#付録-b-旧い型の-brief-を-proof-に移す)。

### A.1 旧い6章（2026-07-30・PR #720 から）

見出しは**番号付き**で書く。目次（§1〜§6）と本文はこの番号で揃う。

| 章 | JA 見出し | EN 見出し | 役割 |
|---|---|---|---|
| §1 | `## 1. TL;DR` | `## 1. TL;DR` | 結論。落差を文章として溶かす |
| §2 | `## 2. 何が起きたか` | `## 2. What happened` | 概要 bullet＋攻撃の連鎖（番号付き） |
| §3 | `## 3. 時系列 — 公表と対応` | `## 3. Timeline — disclosure and response` | 開示・パッチ・業界反応 |
| §4 | `## 4. なぜ止まらなかったか` | `## 4. Why it wasn't stopped` | 構造的論点。✓検出は効いた／✕証明が無かった を本文で |
| §5 | `## 5. 証明があれば、何が変わるか` | `## 5. What proof would have changed` | 処方（report では `## 5. 対策するには` / `## 5. How to counter this`） |
| §6 | `## 6. Sources` | `## 6. Sources` | 一次ソース |

- **「検出と証明の落差」は独立章にしない。** §4 と §5 の骨格そのものにする（落差の要約は TL;DR の結びが担う。旧 gap_* パネルは退役）。
  「検出と証明の落差」「構造的」はブランド語なので、章名から消えても**本文の語彙としては使い続ける**。
  「structural gap」の連語だけは「検出と証明の落差」に統一する。
  （proof では「証明」「落差」を図と本文で使わない・[2.9](#29-呼び名と言い過ぎない)。）

**§1 TL;DR**

- **数文で短く**。詳細は §2 以降に押し出す。検索語（製品名・事案名）を前方に。末尾の「§1…§8 参照」のような番号羅列は禁止。
- 結びは **「効かなかったのは、…する層である。」で断ち切る**。「検出と事前証明は代替でなく補完である」の定型文は
  **TL;DR に入れない**（補完のポジショニングは §4・§5 が担う）。
- 型：「検出は効いていた。効かなかったのは、◯◯を独立に確かめる層である。」の対比を太字で立てるとよい（047 参照）。
- **3 段落目**は「（気づいていたが）◯日に◯◯は通った。効かなかったのは…層である。」の 2 文。§4 で検出の経緯を言い直さない（2026-10-21・069 から）。

**§2 何が起きたか**

- 事実のみ。**概要 bullet**（被害規模・主体・調査方法・公式情報など）→ 接続文（「攻撃は次の連鎖で成立している。」等）→ **連鎖の番号付きリスト**。
- 「核心」「根本原因」の digest bullet は書かない（§4 の冒頭文が担う。重複する）。
- 攻撃・侵入経路の公表された範囲はここに書く（[2.3](#23-02-通った操作)）。

**§3 時系列 — 公表と対応**

- 順序：タイムライン ul → 注記 blockquote（一次ソースの限定・研究環境である旨など）→ 「公表後の対応と業界の動きは次のとおり。」→ 対応・業界動向 bullet。
- **見出しに「時系列」（EN: Timeline）を必ず含める** — 直後の ul が縦線＋ライム縁ドットのタイムライン装飾になるトリガー。
- 時系列は日付だけのラベル（[2.6](#26-05-事実と時系列) と同じ）。
- 実地侵害でない研究実証は、その旨を §3 の注記で明示し被害規模を誇張しない。実名の二層基準の「どこまでが一次か」もここ。

**§4 なぜ止まらなかったか — 圧縮の律**

- **連結でなく圧縮**。短い段落 3〜4 本＋引用ブロックが目安。
- 冒頭は結論の一文：「この事案の失敗は、◯◯でも◯◯でもない。**…を独立に確かめる層が無かった**ことにある。」
- 続けて「検出は効いていた。…効かなかったのは、その手前である。」を **1 段落に畳む**（検出の成功列挙と限界の言い直しを重複させない）。
- カテゴリ帳簿文を書かない（[5.6](#56-書かないもの)）。
- 印象的な引用（当事者・研究者の言）は blockquote に逃がす。
- 関連 Brief への接続は 1 段落に圧縮する。
- report の §4 は「冒頭の結論 2 文 → 図表 2 → 検出が働いた範囲と落差（3 文まで）→ 関連 Brief 1 文」。
  関連 Brief は事案名と一言の括弧書きで足りる（下にカードが出る）（2026-10-21・069 から）。

**§5 証明があれば、何が変わるか（report では「対策するには」）**

- 処方の段落（事前証明が経路のどこに 1 段挟まるか）→ Lemma の設計 bullet（行動前の認可証明・来歴バインド・スコープ・選択的開示など事案に合う軸）→
  検出との相補で締める。「代替ではなく補完」はここで書く。
- 業務ワークフロー事故の書き方・表の決まり・業界の説明を表の後で繰り返さないことは、proof の 04 と同じ（[2.5](#25-04-lemma-でできること)）。

**§6 Sources**：[2.7](#27-06-sources) と同じ。

### A.2 旧い型の題名

実際の Brief がそろって守っているのに書かれていなかった規則（2026-09-12 に直近 11 本を数えて確認）。
**proof の題名は「社名：何が起きたか」だけで、`—` の後半を付けない（[2.8](#28-表紙と目立つところ)）。** 下の後半の決まりは旧い型だけ。

```yaml
title: "<日本語タイトル — サブタイトル（— で区切ると 2 行目がライム縦罫のサブに）>"
title_en: "<English title — subtitle>"
```

- **`—` の前半に、検索の取っ掛かりになる固有名を前方から置く**（製品名・組織名・脆弱性名・コードネーム）。ランキングや一覧は前半しか出さないので、
  ここに固有名が無いと引けない。11 本中 10 本がこの形。例：`x402 決済のファシリテーター 15 社すべてで…` / `ServiceNow AI Platform で、…`
- 固有名を頭に立てたいときは **`名前：` のコロン形**も使う。例：`IDScan.net：本人確認のために窓口へ渡した…`
- **出典・識別子は前半の末尾に丸括弧で**置く。例：`…10時間未満で侵害した(Unit 42調査)` / `…機能していた(CVE-2026-59822、CISAが実悪用を確認しKEV登録)`
- H1 は**平叙文**（「〜した／〜された」）。体言止めにしない。
- 後半（`—` の後ろ）は**何が構造的に欠けていたか**を 1 文で。例：`— 支払いの検証と決済の確定が、行動の前に結び付いていない`
- 表紙の `key_figures` に出す数字はタイトルに入れない（[2.8](#28-表紙と目立つところ)）。
- `title_en` も同じ原則。

### A.3 report レイアウト（opt-in・2026-10）

frontmatter に `layout: "report"` を書いた Brief だけが、レポート型の面で描画される（見本：032）。書かない Brief はこれまでどおりの面のまま。
旧い6章と上の各章の規則はそのまま守る。

- **オンになるもの**：スレートの表紙（`brief_no` を種にした生成グラフィック＋`key_figures`）、表紙下のメタ行（事案日／公開／改訂／発行）、
  「01 見出し」形式の章見出し、目次だけの右レール（脅威バナー・ブランド面は出ない）、部品の CSS（[5.1](#51-普通の-markdown-から組み立てる部品)）。
  冒頭の改訂注記 blockquote は描画されず、版と日付はメタ行に出る（md には残す——dateModified がここから読む）。「参照: 」はカードにならず 1 行のまま。
- **§3 は接続文（「公表後の対応と業界の動きは次のとおり。」）の代わりに `### 公表後の対応` の小見出しを置いてよい。**
- **§5 の見出しは `## 5. 対策するには`**（EN: `## 5. How to counter this`）。読者が自社で何をすればよいかを書く章で、製品の処方ではない。
- `self_check` のカードは表紙のメタ行の下・TL;DR の上に出て、「対策を見る」ボタンは §5 へ飛ぶ。
- `glossary` は §2 の最初のブロックの直後に「用語メモ」として出る。`insight.quote` は §4 の最初の段落の直後に「この事案の核心」の帯で出る。
- `stop` の無い Brief の帯は「この事案の核心」のまま（核心を言い切る一般論の 1 文・「別々の事実である」型の言い回しにしない）。
- 似た事例の入口は、2 章（何が起きたか）のあとの 1 行と 5 章（対策するには）のあとのブロック（[5.8](#58-記事の入口とセルフチェック)）。

## 付録 B 旧い型の Brief を proof に移す

- **旧い型の Brief は、直近 90 日の閲覧数の順に 8 本ずつ** proof の6章に移す。
- 1 本 1 担当で並行に書き、共通の指示を 1 ファイルで渡す。
- 事実は旧本文だけ（出典の無い記述は外し、言い過ぎは弱める・[3.5](#35-出典と言い切り)）。`gate` と `controls` は変えない。
- 表は実行を止める対策だけを行にする（[2.5](#25-04-lemma-でできること)）。推定の状態語は PR に一覧で示す。
- 題名から `—` の後半と `key_figures` の数字を外し、帯を書き直して `insight.stop: true` を付ける（[2.4](#24-03-実行前の照合)）。
- 確かめる順：検査 → 表の読み直し → ビルド → OG の目視。本人の OK でマージする。
