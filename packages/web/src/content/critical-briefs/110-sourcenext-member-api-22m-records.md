## 1. TL;DR

2026 年 10 月 9 日 10 時ごろから、ソースネクストの会員情報システムに第三者が不正にアクセスし、会員情報取得 API を使って登録情報を取得した。最大 22,519,960 件の会員情報が外部に流出した可能性があると、同社が 10 月 15 日に公表した。含まれうる項目は、メールアドレス、パスワード、氏名、住所、電話番号、生年月日などで、クレジットカード情報は対象のシステムに保管されていない。

公表から読む限り、使われたのは、会員情報を返すという API の正規の機能である。認証をどう通ったか、どの脆弱性が使われたかは公表されていない。取得の開始から確認まで、約 4 日が空いた。

確認してからの対応は速かった。同社は 10 月 13 日 9 時ごろに不正アクセスを確認し、同日 13 時 36 分までに封じ込めを完了している。効かなかったのは、会員情報取得 API の呼び出しが、正規の主体・用途・量の範囲内かを、取得のたびに確かめる層である。

## 2. 何が起きたか

- **システム**: 会員情報を管理するシステム。ソースネクストの各サービスの会員が対象で、10 月 13 日 13 時 36 分時点の登録者が範囲とされる。
- **アクセスの性質**: 第三者が、会員情報取得 API を使って登録情報を取得した（公式告知による）。公式の FAQ は「管理するサーバーへの不正アクセス」と記し、API の記述はない。認証をどう通ったか、どの脆弱性が使われたかは、公表されていない。
- **規模**: 最大 22,519,960 件。流出した可能性であって、確定の件数ではない。全項目がすべての会員にあるわけではない。
- **含まれうる項目**: メールアドレス、パスワード、氏名（カナを含む）、住所、性別、電話番号、FAX 番号、生年月日、会社名、役職、部署、利用サービス・登録日・ログイン日などのシステム固有情報。
- **含まれない項目**: クレジットカード情報（対象のシステムに保管なし）。
- **確認されていないこと**: 第三者による悪用の有無。パスワードの保管形式（ハッシュ化の有無）は、公表されていない。

## 3. 時系列 — 公表と対応

- **2026-10-09 10:00 頃**: 不正アクセスの開始（その後の調査で判明した時点）。
- **2026-10-13 09:00 頃**: ソースネクストが不正アクセスを確認。13:36 までに封じ込めを完了。
- **2026-10-15**: 公表。個人情報保護委員会へ報告。ログイン時にパスワードの再設定を求める措置。
- **2026-10-16**: 所轄警察署へ相談（FAQ による）。

> 本件の事実は、ソースネクストの公式告知と FAQ に拠る。「4 日」は開始（10 月 9 日 10 時ごろ）と確認（10 月 13 日 9 時ごろ）の差で、確認の契機は公表されていない。外部のフォレンジック調査が進行中であり、手口、使われた脆弱性、取得の実際の件数は、今後の発表で変わりうる。同社は 2023 年にも、サイトのシステムの一部の脆弱性を突いた不正アクセスで、決済のアプリケーションが改ざんされ、約 12 万人分の個人情報（うちクレジットカード情報 112,132 件）が漏えいした可能性があると公表している（同社の 2023-02-14 の公式告知）。

### 公表後の対応

- **パスワードの無効化**: 流出の対象に含まれるパスワードを順次無効にし、ログイン時に再設定を求めている（FAQ）。
- **脆弱性の修正**: 対象システムの脆弱性を修正し、他の脆弱性の有無を調査している。
- **対象者への案内**: 登録メールアドレスへの通知と、専用の問い合わせ窓口。
- **注意喚起**: 同じパスワードを使っている他のサービスでも変更し、なりすましのメール・SMS・電話に注意するよう求めている。

## 4. なぜ止まらなかったか

この事案の失敗は、第三者が会員情報取得 API に届いたことだけではない。公表から読む限り、API が会員情報を返すという正規の機能が、呼び出す主体・用途・量の対応を確かめられないまま、約 4 日にわたって使われたことにある。

確認してからの対応は速かった。同社は不正アクセスを確認し、当日のうちに封じ込めた。ただし、確認は取得の開始から約 4 日後である。効かなかったのは、その手前である。API が「会員情報を返す」ことと、その呼び出しが「許された主体が、許された用途で、許された量を取る」ことは別の事実であり、後者を呼び出しの直前に確かめる層が、公表された範囲では見当たらない。会員 2,000 万件超という規模が、約 4 日の間に取得されうる状態が、そのまま残っていた。

不正アクセスに気づくことと、呼び出しが許されていると確かめることの間にある隔たりが、本 Brief の言う**検出と証明の落差**である。

対応は、遮断、脆弱性の修正、パスワードの無効化、調査である。これらは必要だが、いずれも取得が行われた後に働く。取得されたパスワードの無効化は、取得された情報の価値を下げるためのものであり、取得の時点を守るものではない。

同じ構造は、これまでの Brief にも現れている。[デンマーク CPR](https://lemma.frame00.com/ja/critical/briefs/152-denmark-cpr-lawful-access-misuse/) では、正規の照会権限による取得が、量と用途の確認なしに約 880 万人分に及んだ。[McHire/Paradox.ai](https://lemma.frame00.com/ja/critical/briefs/056-mchire-paradox-recruiting-auth/) では、採用 AI の API から 6,400 万件にアクセスできた。いずれも、取得の経路が機能として存在するため、実行の直前に独立した確認が置かれていない。

## 5. 対策するには

**侵入の経路が公表されていなくても、API が誰に、何のために、どれだけ返すかは、組織の側で決めて確かめられる。** 会員情報を返す API は、呼び出しが通れば、その機能どおりに情報を返す。呼び出せる相手と用途を決め、一度に、また一定の時間に返せる量に上限を置き、超える取得は実行の前に止める。そうしておけば、経路がどこであっても、取られる量は上限で止まり、取られた範囲も後から言える。

### 注意したい業界・業務

- **業界 · サービス・小売**: ソフトウェアやオンラインショップなど、多数の会員をメールアドレスとパスワードで管理するサービス。会員の数だけ、流出したときの影響が大きい。
- **業務 · 照会・参照**: 会員情報を API や管理画面から引き出す業務。呼び出しが通るかどうかだけで、何件取れるかが決まっていると、正規の機能のまま大量の取得が通る。

同じ穴は、会員を持つ多くのサービスにある。API の入口は守っていても、通った呼び出しが何件を、何のために取っているかを、その場で見ている組織は多くない。

### いまの対策で埋まるか

| 対策 | 今回 | 理由 |
| --- | --- | --- |
| API の認証（呼び出し元の鍵・トークン） | 一部 | 呼び出せる相手を絞る。ただ、今回認証をどう通ったかは公表されておらず、通った呼び出しが何件を取るかは見ない。 |
| 侵入の検知と遮断 | 一部 | 確認から同日中に封じ込めた。ただ、確認は取得の開始から約 4 日後で、その間に取られた分は戻らない。 |
| パスワードの無効化と再設定 | 一部 | 取られたパスワードでのログインは防ぐ。同じパスワードを使い回した、ほかのサービスには及ばない。 |
| 脆弱性の修正 | 一部 | 今回の穴からの再侵入は防ぐ。別の経路から届いた呼び出しが何件を取るかは見ない。 |

### 必要になるもの

1. **呼び出せる相手と用途を、付与の時点で決めて記録する。** 会員情報を返す API ごとに、誰が、何のために、どの範囲の会員を引けるかを決める。決めた内容を、呼び出しのたびに照合できる形で残す。
2. **量と対象に上限を置き、超える取得は実行の前に止める。** 1 回の呼び出し、一定の時間に返せる件数と、対象にできる会員の範囲を決める。超える呼び出しは、確かめられるまで保留にする。
3. **誰の何を取ったかを、呼び出す側とは別に残す。** どの許可に基づいて、誰の何が返されたかを、呼び出す側の操作とは別の記録として残す。取られた後に、範囲を自分たちの記録で言えるようにする。

### 点検チェックリスト

会員情報を返す API について、組織で確かめる 3 項目

- 会員情報を返す API を一覧で言えるか。それぞれ、誰が何のために呼び出すかが決まっているか。
- 1 回の呼び出し、1 日の呼び出しで返せる件数に上限があるか。超えたとき、誰に知らせが届き、取得を止められるか。
- 取得された会員の範囲を、API を呼び出した側の記録に頼らずに言えるか。

注：正規の主体が範囲内で目的外に使う場合や、上限の内側で少しずつ取られる場合は、この仕組みでも通ってしまう。また、上限を置くと、正規の一括処理も止まったり遅れたりする。今回は手口と使われた脆弱性が公表されていない。続報で判明すれば、この Brief を改訂する。
