## 1. 要点

公表から読む限り、使われたのは、会員情報を返すという API の正規の機能である。認証をどう通ったか、どの脆弱性が使われたかは公表されておらず、取得の開始から確認まで、約 4 日が空いた。確認してからの対応は速く、同日のうちに封じ込めた。<strong>会員情報を返す API は、返す前に呼び出しの範囲を照合しなければ、範囲の外の取得も、同じ機能の呼び出しとして通る。</strong>

## 2. 通った操作

- **通った操作**: 会員情報取得 API の呼び出しによる、登録情報の取得。2026 年 10 月 9 日 10 時ごろから始まった（ソースネクスト）。
- **止まった操作**: 10 月 13 日 9 時ごろに不正アクセスを確認し、同日 13 時 36 分までに、外部からの不正な通信を遮断するなどして封じ込めを完了した。取得が始まってから約 4 日後である。
- **受け付けた側に届くもの**: 一般に、API の呼び出しは、鍵やトークンが通れば、その機能どおりに情報を返す呼び出しとして届く。その呼び出しが、許された主体・用途・量の範囲内かは、呼び出しからは区別できない。
- **公表されていないこと**: 認証をどう通ったか、使われた脆弱性、パスワードの保管形式（ハッシュ化の有無）、第三者による悪用の有無。外部のフォレンジック調査が進行中で、取得の実際の件数は変わりうる。公式告知は「会員情報取得 API」、FAQ は「サーバーへの不正アクセス」と記し、表記が一致しない。

## 3. 実行前の照合

経路を問わず区別できる条件は、会員情報を返す側が、API の呼び出しが、許された主体・用途・量の範囲内かを、返す前に、呼び出す側とは別に照合することである。

- **誰が承認を出すか**: 会員情報を管理する組織。会員情報を返す API ごとに、誰が、何のために、どの範囲の会員を引けるかを、付与の時点で決めて記録する。呼び出す側の申告だけには頼らない。
- **どこで照合するか**: API が情報を返す手前。1 回の呼び出し、一定の時間に返せる件数と、対象にできる会員の範囲に上限を置き、許可の範囲を超える取得は、照合が済むまで保留にする。
- **何が残るか**: どの許可に基づいて、誰の何が返されたかの記録。呼び出す側の操作とは別に、後から第三者に示せる形で残す。

検知は働いたが、気づいたのは取得が始まってから約 4 日後だった。同じように、取得の経路が機能として存在するため、実行の直前に独立した確認が置かれていなかった事案に、[デンマーク CPR](https://lemma.frame00.com/ja/critical/briefs/152-denmark-cpr-lawful-access-misuse/)と[McHire/Paradox.ai](https://lemma.frame00.com/ja/critical/briefs/056-mchire-paradox-recruiting-auth/)がある。

## 4. Lemma でできること

**Lemma は、03 の照合を、会員情報を返す API の手前に組み込む。** 侵入を見つけるのではなく、API の呼び出しが、許された主体・用途・量の範囲内かを、返す前に照合する。

### 注意したい業界・業務

- **業界 · サービス・小売**: ソフトウェアやオンラインショップなど、多数の会員をメールアドレスとパスワードで管理するサービス。会員の数だけ、流出したときの影響が大きい。
- **業務 · 照会・参照**: 会員情報を API や管理画面から引き出す業務。呼び出しが通るかどうかだけで、何件取れるかが決まっていると、正規の機能のまま大量の取得が通る。

### いまの対策と Lemma の違い

今回の経路は 1 列目（会員情報取得 API の呼び出し）である。2 列目は、取られたパスワードでのログインで、取得の後に起きる。

| 対策 | 会員情報取得 API の呼び出し | 取られたパスワードでのログイン |
| --- | --- | --- |
| API の認証（呼び出し元の鍵・トークン） | 一部 | 関係しない |
| 侵入の検知と遮断 | 一部 | 関係しない |
| パスワードの無効化と再設定 | 関係しない | 一部 |
| 脆弱性の修正 | 一部 | 関係しない |
| **Lemma（実行の前の照合）** | 効く | 関係しない |

API の認証は、呼び出せる相手を絞るが、今回認証をどう通ったかは公表されておらず、通った呼び出しが何件を取るかは見ない。侵入の検知と遮断は、確認から同日中に封じ込めたが、確認は取得の開始から約 4 日後で、その間に取られた分は戻らない。パスワードの無効化と再設定は、取られたパスワードでのログインを防ぐが、同じパスワードを使い回した、ほかのサービスには及ばず、取得の時点を守るものでもない。脆弱性の修正は、今回の穴からの再侵入を防ぐが、別の経路から届いた呼び出しが何件を取るかは見ない。Lemma は、返す前に、呼び出しを許可の範囲と照合する。

注：Lemma の照合が働くのは、会員情報を返す API の手前に照合を組み込み、呼び出せる相手・用途・量の許可を、呼び出す側とは別に管理している場合に限る。正規の主体が範囲内で目的外に使う場合や、上限の内側で少しずつ取られる場合は、この照合を通ってしまう。また、上限を置くと、正規の一括処理も止まったり遅れたりする。今回は手口と使われた脆弱性が公表されていない。続報で判明すれば、この Brief を改訂する。表は何を照合しているかの比較で、今回の事案で止まったかどうかを示すものではない。Lemma は、侵入を検出・防止するものではない。

### 点検チェックリスト

会員情報を返す API について、組織で確認する 3 項目

- 会員情報を返す API を一覧で言えるか。それぞれ、誰が何のために呼び出すかが決まっているか。
- 1 回の呼び出し、1 日の呼び出しで返せる件数に上限があるか。超えたとき、誰に知らせが届き、取得を止められるか。
- 取得された会員の範囲を、API を呼び出した側の記録に頼らずに言えるか。

## 5. 事実と時系列

- **システム**: 会員情報を管理するシステム。ソースネクストの各サービスの会員が対象で、10 月 13 日 13 時 36 分時点の登録者が範囲とされる。
- **アクセスの性質**: 第三者が、会員情報取得 API を使って登録情報を取得した（公式告知による）。公式の FAQ は「管理するサーバーへの不正アクセス」と記し、API の記述はない。認証をどう通ったか、どの脆弱性が使われたかは、公表されていない。
- **規模**: 最大 22,519,960 件。流出した可能性であって、確定の件数ではない。全項目がすべての会員にあるわけではない。
- **含まれうる項目**: メールアドレス、パスワード、氏名（カナを含む）、住所、性別、電話番号、FAX 番号、生年月日、会社名、役職、部署、利用サービス・登録日・ログイン日などのシステム固有情報。
- **含まれない項目**: クレジットカード情報（対象のシステムに保管なし）。

### 時系列

- **2026-10-09**: 10:00 ごろ、不正アクセスが始まる（その後の調査で判明した時点）。
- **2026-10-13**: 09:00 ごろ、ソースネクストが不正アクセスを確認。13:36 までに封じ込めを完了。
- **2026-10-15**: 公表。個人情報保護委員会へ報告。ログイン時にパスワードの再設定を求める措置。
- **2026-10-16**: 所轄警察署へ相談（FAQ による）。

> 本件の事実は、ソースネクストの公式告知と FAQ に拠る。「4 日」は開始（10 月 9 日 10 時ごろ）と確認（10 月 13 日 9 時ごろ）の差で、確認の契機は公表されていない。外部のフォレンジック調査が進行中であり、手口、使われた脆弱性、取得の実際の件数は、今後の発表で変わりうる。公表されていないことは、対策が無かったことを意味しない。同社は 2023 年にも、サイトのシステムの一部の脆弱性を突いた不正アクセスで、決済のアプリケーションが改ざんされ、約 12 万人分の個人情報（うちクレジットカード情報 112,132 件）が漏えいした可能性があると公表している（同社の 2023-02-14 の公式告知）。

### 公表後の対応

- **パスワードの無効化**: 流出の対象に含まれるパスワードを順次無効にし、ログイン時に再設定を求めている（FAQ）。
- **脆弱性の修正**: 対象システムの脆弱性を修正し、他の脆弱性の有無を調査している。
- **対象者への案内**: 登録メールアドレスへの通知と、専用の問い合わせ窓口。
- **注意喚起**: 同じパスワードを使っている他のサービスでも変更し、なりすましのメール・SMS・電話に注意するよう求めている。
