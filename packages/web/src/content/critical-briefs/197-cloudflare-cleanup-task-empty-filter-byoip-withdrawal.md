## 1. 要点

2026 年 2 月 20 日、Cloudflare の BYOIP（顧客が持つ IP アドレスを Cloudflare から広告するサービス）で、顧客のプレフィックスの経路が BGP で取り下げられた。同社の事後報告によれば、17:56 から 18:46 UTC の間に約 1,100 件のプレフィックスが取り下げられ、これは BYOIP の 4,306 件の約 25% にあたる。CDN とセキュリティ・Spectrum・Dedicated Egress・Magic Transit を使う一部の顧客で接続が失敗し、すべて戻ったのは 23:03 UTC だった。同社は、攻撃ではなく社内の変更が原因としている。

原因は、顧客が削除を求めたプレフィックスを定期的に探して消す、掃除用の処理だった。処理は pending_delete という条件を値なしで渡し、API は空の値を「すべての BYOIP プレフィックス」の要求と解釈した。処理は、プレフィックスとサービスの結びつけなどの関連する設定を順に消し、技術者が気づいて止めるまで続いた。同社は、API の条件の型の見直し、設定の配布を戻せる形にすること、速すぎる・広すぎる変更で配布を止める仕組みを挙げている。

<strong>削除の対象を決める条件は、空でも誤りでも、受け付ける側には正しい依頼と同じ形で届く。</strong>

## 2. 通った操作

- **通った操作**: Addressing API に対する、BYOIP のプレフィックスと関連する設定の削除。2 月 5 日に取り込まれ、2 月 20 日 17:46 UTC に本番に出た掃除用の定期処理が、17:56 UTC から実行した。処理は、削除待ちのプレフィックスを探す照会で pending_delete を値なしで渡し、API はこれを、削除待ちのものではなくすべての BYOIP プレフィックスの要求として扱った（同社の事後報告）。
- **受け付けた側に届くもの**: 一般に、設定を管理する API には、正規の処理からの照会と削除の要求が届く。照会の条件が意図どおりか、返った件数が顧客の依頼の数と合うかは届かない。同社によれば、試験は顧客が使うセルフサービスの API の経路に集中し、処理が明示の入力なしに利用者のデータを変える場合を見落としていた。試験の環境のデータは本番に十分近くなかった。
- **公表されていないこと**: 定期処理がどれだけの間隔で動いていたか。削除待ちだったプレフィックスの本来の件数。影響を受けた顧客の数（同社は、すべての BYOIP の顧客が影響を受けたわけではないとする）。処理が 1 回に消せる件数に上限があったか。

## 3. 実行前の照合

経路を問わず区別できる条件は、定期処理が顧客の設定を消す前に、対象の件数と範囲を、処理自身の照会の結果とは別に、顧客が出した削除の依頼の記録と照合することである。

- **誰が承認を出すか**: プレフィックスの持ち主である顧客。ダッシュボードや API で削除を依頼したときに、どのプレフィックスを消すかの記録を、掃除用の処理では作れない形で残す。
- **どこで照合するか**: 掃除用の処理が削除を実行する手順。照会で返った対象が、削除の依頼の記録と件数・プレフィックスごとに合わないとき、条件が空や未指定のとき、1 回の件数が上限を超えるときは、実行の前に保留する。
- **何が残るか**: どの処理が、どの条件で、どの顧客のどのプレフィックスと結びつけを消したかの記録。元の状態とともに処理とは別に残し、戻すときの手がかりにする。

処理が止まったのは取り下げが始まってから 50 分後で、すべて戻るまでにはさらに約 4 時間かかった。AI エージェントが、本番のデータを消す操作を人の承認なしに実行した事案に [PocketOS](https://lemma.frame00.com/ja/critical/briefs/007-pocketos-cursor-db-deletion/)（API の 1 回の呼び出しで本番のデータベースとバックアップが消えた）と [Replit](https://lemma.frame00.com/ja/critical/briefs/080-replit-agent-code-freeze-data-loss/)（変更禁止の最中に本番のデータベースを消した）がある。今回は AI ではなく、人が書いた正規の定期処理が、空の条件で対象を絞らないまま、顧客の設定を消した。

## 4. Lemma でできること

**Lemma は、実行前の照合を、掃除用の処理が顧客の設定を消す手順に組み込む。** 障害を見つけるのではなく、消す対象が顧客の削除の依頼に基づくかを、実行の前に照合する。

### 注意したい業界・業務

- **業界 · 開発者・IT**: 顧客の設定やリソースを、定期処理や自動化で作り、変え、消すクラウドやネットワークの事業者。1 つの処理が、多くの顧客の設定に届く。
- **業界 · 調達・サプライチェーン**: IP アドレスの広告やネットワークの経路を、外部の提供元に任せる会社。今回、Laravel Cloud は、自社の基盤は動いたまま約 3 時間 15 分つながらなかったとしている。
- **業務 · 承認・決裁**: 顧客の設定を消す一括の操作と、その範囲（件数・対象）の確認。

### いまの対策と Lemma の違い

今回の経路は 1 列目（定期処理が、条件の誤りで依頼の範囲を越えて消した）である。2 列目は、人の運用者が誤った条件で一括の削除を出す場合で、今回そうだったという公表は無い。3 列目は、消えた設定を元に戻すことで、どの対策も実行を止める・絞るものなので、ここには効かない。

| 対策 | 定期処理の条件の誤り | 人の運用者の誤った一括削除 | 消えた設定を元に戻す |
| --- | --- | --- | --- |
| コードレビューと試験 | 一部 | 効かない | 効かない |
| 接続の監視と検知 | 一部 | 一部 | 効かない |
| 速すぎる・広すぎる変更で配布を止める仕組み（同社の再発防止策） | 一部 | 一部 | 効かない |
| **Lemma（実行の前の照合）** | 効く | 効く | 効かない |

コードレビューと試験は、誤りを本番の前に見つけるが、今回はセルフサービスの経路に集中し、明示の入力の無い場合を見落とした。監視と検知は、今回 1.1.1.1 の失敗で働いたが、約 50 分の間に約 1,100 件が取り下げられた後だった。同社が挙げた変更の遮断は、変更の速さと広さを見るもので、上限より小さい誤った削除は通りうる。Lemma は、変更の量ではなく、消す対象が顧客の削除の依頼の記録と合うかを、実行の前に照合する。

注：Lemma の照合が働くのは、掃除用の処理が削除を実行する手順に照合を組み込み、顧客の削除の依頼の記録を処理の照会とは別に管理する場合に限る。依頼の記録そのものが誤っていれば、照合を通りうる。表は何を照合しているかの比較で、今回の事案で止まったかどうかを示すものではない。Lemma は、障害を検出するものではなく、消えた設定やデータを元に戻すものでもない。

### 点検チェックリスト

顧客の設定を変え、消す自動処理について、組織で確認する 3 項目

- 自動処理に渡す条件が空や未指定のとき、API が「すべて」と解釈せず、要求を拒む形になっているか。
- 試験の環境に本番に近い件数と形のデータがあり、明示の入力なしに利用者のデータを変える経路を試験しているか。
- 自動処理が設定を消したとき、どの顧客の何を消したかを記録から特定し、顧客の操作を待たずに元の状態へ戻せるか。

## 5. 事実と時系列

- **当事者**: Cloudflare, Inc.（米国）と、同社の BYOIP を使う顧客。本 Brief は、同社の事後報告と Cloudflare Status の記録（いずれも一次）、影響を受けた顧客の Laravel Cloud の事案報告に拠る。
- **起きたこと**: 同社の事後報告によれば、Code Orange: Fail Small の取り組みの一部として、顧客が手で依頼していた BYOIP のプレフィックスの削除を自動にする変更を入れた。その中の、削除すべきプレフィックスを定期的に探して消す処理が、pending_delete を値なしで渡し、サーバーの側は空の値を、削除待ちのものではなくすべての BYOIP プレフィックスの要求と解釈した。処理は、すべての BYOIP プレフィックスと、サービスの結びつけを含む関連する設定を順に消し始め、技術者が気づいて止めるまで続いた。変更が一度にではなく順に適用されたため、影響は顧客ごとに異なった。
- **影響**: 17:56 から 18:46 UTC の間に、ある接続先に広告していた 6,500 件のプレフィックスのうち約 1,100 件が取り下げられた。BYOIP は 4,306 件で、その約 25% にあたる。CDN とセキュリティのサービスでは影響を受けたサイトへの接続が失敗し、Spectrum のアプリは通信を中継できず、Dedicated Egress の顧客は宛先に通信を送れず、Magic Transit で守られたアプリは時間切れになった。1.1.1.1 のウェブサイトは HTTP 403 を返したが、1.1.1.1 での DNS の名前解決（DNS over HTTPS を含む）には影響が無かった。同社は事案の長さを 6 時間 7 分とする。
- **戻すのに時間がかかった理由**: プレフィックスによって影響の受け方が違った。経路の取り下げだけのものは顧客がダッシュボードから広告し直せたが、結びつけの一部や全部が消えたものは戻せなかった。約 300 件は、ソフトウェアの不具合でサービスの設定がエッジから消えており、ダッシュボードから戻せず、エッジのすべての機械に設定を配り直した。
- **見落とされた理由**: 同社によれば、試験の環境のデータは本番に十分近くなく、模擬のデータも足りなかった。試験と当初のコードレビューは、顧客が使うセルフサービスの API の経路に集中し、処理が明示の入力なしに利用者のデータを変える場合を対象にしていなかった。

### 時系列

- **2026-02-05**: 掃除用の処理を含むコードが取り込まれる（21:53 UTC）。
- **2026-02-20**: 17:46 UTC にその版が本番に出る。17:56 に処理が動き、取り下げが始まる。
- **2026-02-20**: 18:13 に 1.1.1.1 の失敗で対応が始まり、18:18 に社内で事案を宣言し、18:21 に Addressing API の担当を呼ぶ。18:45 に Cloudflare Status に最初の掲載。18:46 に技術者が処理を止め、定期の実行を無効にする。
- **2026-02-20**: 19:19 に顧客がダッシュボードから広告し直せるようになる。20:30 に結びつけの残るプレフィックスを戻す版を出す。21:08 にエッジ全体への設定の配布を始め、23:03 に終わって影響が終わる。23:50 に Cloudflare Status で解決とする。
- **2026-02-21**: 同社が事後報告を公表する。

> 本件の事実は、Cloudflare の事後報告と Cloudflare Status の記録（いずれも一次）に拠る。事後報告は冒頭で始まりを 17:48 UTC、時系列で影響の始まりを 17:56 UTC と書いており、本 Brief は時系列の値を使う。取り下げられた割合の「約 25%」は、事後報告では BYOIP のプレフィックスの割合で、顧客の割合ではない。影響を受けた顧客の数、定期処理の実行の間隔、本来の削除待ちの件数は公表されていない。Laravel Cloud の時刻は同社の事案報告に拠る。公表されていないことは、対策が無かったことを意味しない。本 Brief は、同社の対応を評価するものではない。11 月 10 日時点の記述。

### 公表後の対応

- **Cloudflare**: 再発防止として、文字列で扱っていた pending_delete の条件を、検証しやすい標準の型に改める。顧客が変えた設定と、本番で動く状態を分け、設定のスナップショットを健全性を見ながら配り、すぐ戻せるようにする。プレフィックスの大量の取り下げや削除のような、速すぎる・広すぎる変更を検知して配布を止める仕組み（サーキットブレーカー）を入れ、顧客のサービスが正しく動いているかの信号もその判断に使う。いずれも Code Orange: Fail Small の取り組みの一部とした。
- **Laravel Cloud**: 18:42 UTC に自社の監視で接続の失敗に気づき、ダッシュボードからの広告し直しを試みたが、プレフィックスが取り下げの状態に固定されて使えず、21:57 UTC に戻ったとした。顧客のデータの消失は無く、IP の広告の層にも冗長性を広げるとしている。
