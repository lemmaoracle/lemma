## 1. 要点

自治体の防災メールの配信基盤 SpeeCAN RAIDEN が不正アクセスを受け、基盤に置かれたバックドアから、防災メールと同じ送信元ドメインの偽メールが 1,423,428 通配信された（アルカディアの第 12・17 報）。受け取った人に残された手がかりは、送信者名と送信元アドレスの見た目だけで、そのアドレスは本物の防災メールと同じドメインだった。

侵入は、添付ファイルを公開するメディアサーバーのディレクトリパストラバーサルから設定ファイルが取られ、中にあったサービス間ログイン用のシークレットキーで、アカウント ID への総当たりでログインされたものだった（第 12 報）。10 月 22〜23 日には、最初の侵入で漏れたメール送信 API のアカウントと URL パースコンフュージョンの脆弱性で、再び偽メールが送られた（第 25 報）。静岡市は、送信元をブロックすると本物の防災情報も届かなくなると注意している。

<strong>通知の本物らしさを送信元の表示だけに預けると、同じ表示の偽物が届いた時点で、受け取る人は見分けられない。</strong>

## 2. 通った操作

- **通った操作**: 防災メールと同じ `@raiden.ktaiwork.jp` を送信元に含む、クレジットカード会社を装ったメールの、登録者への配信。基盤に置かれたバックドアから、10 月 13 日 1:17 から 7:16 の間に 1,423,428 通が送られた（第 17 報）。少なくとも 869,575 通は、同社が持たないメールアドレス宛てだった。10 月 22〜23 日には、漏れたメール送信 API のアカウントから再び送られた（第 25 報）。
- **侵入の経路**（第 12 報）: 10 月 11 日 6:26 にアクセスが始まり、ログイン画面・API・ファイルサーバーの探索とログインの試行が繰り返された。16:39、添付ファイルを公開するメディアサーバーのディレクトリパストラバーサルで設定ファイル（config.ini）が取られ、中のサービス間ログイン用のシークレットキーが流出した。その鍵でアカウント ID への総当たりでログインされ、セッションから内部情報が取得された。23:40、データベースの異常な負荷を社内の監視が捉え、翌 12 日 3:00 に経路を遮断した。12 日 17:05 に WordPress への不正なプラグイン（バックドア）が見つかり、13 日未明の配信に使われた。
- **止まった操作**: アルカディアは、検知から 3 時間余りで侵入経路を塞ぎ、13 日 7:16 に偽メールの配信を止めた。さいたま市は、住民の問い合わせから 2 分で、事業者に確認を取った。
- **受け付けた側に届くもの**: 一般に、メールを受け取る側に届くのは、送信者名と送信元アドレスの表示である。同じドメインを含むアドレスは、本物の通知と見た目で区別できない。基盤そのものから送られた偽メールは、送信ドメイン認証も正規の経路として通る。防災メールは、受け取った人がすぐに動くことを前提にした通知で、避難情報、職員の参集、ダム放流の連絡は、真偽を確認する時間が短い。
- **公表されていないこと**: 実際に取得された情報の範囲（件数は推定のまま）。総当たりで突破されたアカウントの範囲。偽メールの宛先のうち同社が持たないアドレスの出どころ。第三者機関の脆弱性診断とダークウェブ調査の結果。最終報告。

> 「@raiden.ktaiwork.jp」は、静岡市防災メールで使用している正しい送信元アドレスの一部です。しかし、今回確認されたメールは、これを悪用したなりすましメールであり、クレジットカード会社から送信されたものではありません。
> — 静岡市

## 3. 実行前の照合

経路を問わず区別できる条件は、通知を受け取って動く人が、その通知が自治体の発したものかを、送信元の表示とは別に、動く前に照合できることである。

- **誰が承認を出すか**: 通知を発する自治体。配信する通知の一通ごとに、自治体が自らの鍵で発行元の署名を付ける。鍵は配信基盤に預けないので、基盤のドメインやアドレスを使えても、署名は作れない。発行日時と宛先も署名に含め、過去の本物の通知を送り直しても通らないようにする。
- **どこで照合するか**: 二か所。配信基盤は、届いた配信の指示が、対象の登録者・種別・件数の許可の範囲内かを、送る前に照合し、範囲外は送らない。受け取る人の側は、公式アプリや確認ページで、通知の署名を、動く前に照合する。署名と合わない通知は、送信元の表示が同じでも「自治体のものではない」と示す。
- **何が残るか**: 配信の指示と照合の結果の記録。基盤が侵害されても書き換えられないよう、基盤の外で確認できる形で残す。

同じように、届いた経路の正しさが、書いた主体の正しさの代わりに使われた事案に、[Photo ZIP](https://lemma.frame00.com/ja/critical/briefs/091-photo-zip-authentication-laundering/)（正規の配信基盤を経由したメールが SPF・DKIM・DMARC をすべて通過した）と、[Revolut](https://lemma.frame00.com/ja/critical/briefs/149-revolut-italy-government-mailbox-disclosure-requests/)（国の認証メール網から届いた開示要求が、経路の正しさを理由に通った）がある。今回の偽メールは、基盤に置かれたバックドアと、漏れた送信 API のアカウントから送られた（第 17・25 報）。受け取った人には送信元の表示しか残らない点は同じである。

## 4. Lemma でできること

**Lemma は、実行前の照合を、通知を配信する側と受け取る側に組み込む。** 侵入を見つけるのではなく、配信の指示が許可の範囲内か、届いた通知が自治体の発したものかを、動く前に照合する。そのための仕組みは、配信を委託している自治体の側と、受け取る人の手元の両方に要る。今日すぐに足せるのは、本物の通知を確認する場所を一つ決めて、登録者に知らせておくことである。

### 注意したい業界・業務

- **業界 · 自治体・公共**: 防災情報や避難の呼びかけ、職員の参集連絡を、委託先の一斉配信サービスで送る自治体。受け取る人は、すぐに動くことを求められる。
- **業界 · 金融・FinTech**: 取引の通知や本人確認の連絡を、外部の配信サービスを通してメールや SMS で送る事業者。同じドメインから届く偽の通知は、見た目では区別できない。
- **業務 · 配信・送付**: 登録者や顧客への一斉配信を、外部の基盤に委託する業務。基盤のドメインやアドレスが、そのまま「本物らしさ」の根拠になっている。

### いまの対策と Lemma の違い

今回の偽メールは 1 列目（不正アクセスで配信基盤そのものから送られた通知）である（第 17・25 報）。2 列目は、外から送信元を偽って送られた通知で、今回そうだったという公表は無い。

| 対策 | 基盤から送られた通知 | 外から送信元を偽って送られた通知 |
| --- | --- | --- |
| 送信ドメイン認証（SPF・DKIM・DMARC） | 効かない | 一部 |
| 送信元のブロック・迷惑メール設定 | 効かない | 効かない |
| 不審なメールの URL や添付を開かないよう呼びかける | 一部 | 一部 |
| 配信サービスの停止 | 一部 | 効かない |
| **Lemma（実行の前の照合）** | 効く | 効く |

送信ドメイン認証は、外から送信元を偽った偽メールなら、ドメイン側の設定しだいで、受信側が迷惑メールに振り分けたり拒否したりできる。基盤そのものから送られた場合は、正規の経路として通る。送信元のブロックは、偽物と一緒に、本物の防災情報も止まる（静岡市が注意している）。呼びかけは、今回のようにカード会社を装う内容なら、防災メールらしくないと気づける可能性があるが、自治体の避難情報を装う偽メールは、見た目では区別できない。配信サービスの停止は、基盤から出る配信は止まるが、本物の防災情報も止まる。Lemma は、通知が自治体の発したものかを、署名で、受け取った人が動く前に照合する。

注：Lemma の照合が働くのは、自治体が通知に署名を付け、受け取る人が照合する手段を持ち、配信の指示の照合が基盤とは別に管理されている場合に限る。受け取る人が照合の手段を持たなければ、通知はこれまでどおり見た目で判断される。署名が示すのは、通知が登録された発行元から出たことまでで、基盤への侵入や連絡先の流出そのものは防がない。表は何を照合しているかの比較で、今回の事案で止まったかどうかを示すものではない。Lemma は、侵入を検出・防止するものではない。

### 点検チェックリスト

自分たちの名義の通知を、外部のサービスから送っている組織で確認する 3 項目

- 自分たちの名義の通知を、どの外部サービスから、どのドメインで送っているか。そのサービスが侵害されたとき、受け取った人は本物と偽物をどう見分けるか。
- 配信サービスに、誰が、どの範囲の配信を指示できるか。範囲外の一斉配信を、送る前に止められるか。
- 偽の通知が出回ったとき、送信元をブロックさせずに、本物を確認する方法を登録者に案内できるか。

## 5. 事実と時系列

- **システム**: SpeeCAN RAIDEN。アルカディア(大阪府箕面市)が運営する一斉配信の基盤で、自治体の防災メールや、携帯電話を持たない住民向けの電話・FAX 配信などに使われている。10 月 14 日の続報で、消防向けの 119RAIDEN と、聴覚や言語に障害のある人がスマートフォンから 119 番通報する NET119 にも、不正アクセスの形跡が見つかったと公表された。
- **漏えいの可能性がある情報**: SpeeCAN RAIDEN は連絡先の名前、メールアドレス、電話・FAX 番号、担当者、契約情報、履歴に保存された配信本文(SpeeCAN RAIDEN では決済情報は扱っていないとされる)。NET119 は利用者の名前、生年月日、性別、住所、電話番号、メールアドレス、FAX 番号など。
- **最大推定の件数**: SpeeCAN RAIDEN はメールアドレス約 313.6 万件、電話番号約 10.5 万件、FAX 番号約 1.5 万件。NET119 は約 1.3 万件、119RAIDEN はメールアドレス約 9.7 万件など。アルカディアは「あくまでも推定値」としている。
- **自治体側**: 静岡市は、防災メールの市民 34,336 人分のメールアドレスと、市職員 6,915 人分の氏名・職員番号・所属名が漏えいしたことが判明したと公表した(アルカディアは漏えいを可能性としている)。さいたま市は 34,783 件、横須賀市は防災・防犯メールなど 4 つのサービスで計約 5.9 万人分を漏えいの可能性として挙げた。岡山市は、防災メール約 4,500 件に加え、職員の参集連絡用の約 5,000 件とダム放流の通知先約 350 件が登録されているとした。
- **偽メール**: 静岡市によれば、件名は「＜重要＞ご利用確認のお願い」、送信者名は実在のクレジットカード会社、送信元アドレスは「〇〇@raiden.ktaiwork.jp」。市は「@raiden.ktaiwork.jp」を防災メールで使う正しい送信元アドレスの一部と説明し、届いたメールはそれを悪用したなりすましだとしている。本件と関連している可能性があるメールという位置づけである。松本市・横須賀市にも登録者から同様の通報が寄せられたが、松本市は不正アクセスとの関係は現時点で不明としている。
- **侵入の経路**: アルカディアは第 2 報で「外部からの不正な侵入経路が判明」したとし、侵入経路になっていた 2 つのサービス(SpeeCAN RAIDEN の raiden3.ktaiwork.jp と、学校向けのライデン・スクールの s2.ktaiwork.jp)を緊急停止した。第 12 報(10 月 19 日の PDF)で手口を公表した。添付ファイルを公開するメディアサーバーに、内部の URL にアクセスできるディレクトリパストラバーサルがあり、内部のソースファイルが取得されたことで、設定ファイル内のサービス間ログイン用シークレットキーが取られた。その鍵を使ってアカウント ID への総当たりが行われ、ログインされたセッションから内部情報が取得された。12 日 17:05 に WordPress へ不正なプラグインが追加されていたことが分かり、owner・support 画面のパスワードを変えた。14 日には raiden3 のデータベースで複数の書き換えが見つかり、15 日 9:30 に手作業で直した(ソースコードの改ざんは無し)。NET119・旧 119RAIDEN・社内の会計サブシステムのデータベースにも痕跡があった。
- **偽メールの経路**: 第 17 報によれば、10 月 13 日 1:17 から 7:16 の間に、不正なプログラム(バックドア)から 1,423,428 通が外部に配信され、少なくとも 869,575 通は同社が持たないメールアドレス宛てだった。13 日 0:10 に DKIM・DMARC などのメール送信の試験があり、1:17 から 5 件ずつ、最終的に 1,000 件ずつ送られた(第 12 報)。第 25 報によれば、10 月 22〜23 日には、最初の侵入で漏れたメール送信 API のアカウントのパスワードを総当たりで突破され、外部から API が使われて不正メールが送られた。22 日 6:30 ごろに API の連携を止めたが、URL パースコンフュージョンの脆弱性で再び使われ、23 日 10:30 ごろに脆弱性を解消した。API のアカウントとパスワードを変えてから連携を再開するとしている。

### 公表後の対応

- **配信の停止**: 共同通信によれば、総務省は 13 日午後 9 時時点で 36 自治体がサービスを停止したと明らかにした。横須賀市は防災・防犯メールなど 4 つのサービスを止め、市の SNS や防災行政無線で代わりに発信するとした。岡山市は、停止中は防災メールの登録者への気象・避難情報や、職員への一斉連絡が送れないとした。
- **登録者への注意喚起**: 各自治体は、不審なメールの URL や添付ファイルを開かないよう呼びかけた。静岡市は、市が `@raiden.ktaiwork.jp` から送るのは防災情報だけだとしたうえで、不審メールの送信元をブロックしたり迷惑メールに設定したりすると、市の防災情報も届かなくなると注意している。
- **届出**: アルカディアは、個人情報保護委員会・JIPDEC プライバシーマーク推進センター・総務省近畿総合通信局・ISMS 日本能率協会へ報告し、箕面警察署・大阪府警と協議して被害届を提出予定とした(第 12 報)。契約先に代わる個人情報保護委員会への報告は 10 月 23 日に提出した(第 23 報)。横須賀市も個人情報保護委員会への報告を公表している。
- **アルカディアの再発防止策**(第 12・25 報): 社内で立ち上げた LLM での脆弱性診断とコードレビュー、外部の会社による脆弱性診断、データベースへのアクセスの見直し(サービスごとのパスワード・2 段階認証)、自動監視の強化と SOC の導入の検討、外部連携(X・Facebook・LINE・エリアメールなど)の設定ファイルの見直し、ログインの 2 段階認証の追加、メール送信 API のアカウントとパスワードの変更。
