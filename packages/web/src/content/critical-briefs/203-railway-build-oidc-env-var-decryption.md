## 1. 要点

開発・ホスティングの基盤 Railway（米国）で、攻撃者がビルド基盤の未知の脆弱性からビルド用の認証情報を取り、内部の Temporal（非同期の処理の基盤）からほかのビルドの履歴と社内のモノレポの写しを得た（Railway のインシデント報告）。攻撃者は次に、CI/CD の OIDC の信頼の設定の誤りから、短時間だけ有効なクラウドの認証情報を得た。そこから内部の認証情報を取り、暗号化された環境変数をデータベースから取り出して、鍵管理サービス（KMS）で一部を復号した。

Railway によれば、環境変数のいずれかが復号された可能性があるのは、最大で 1.85%（約 100,000）のワークスペースである。記録が示すのは環境の単位で、個々の変数ではないため、これは上限の値である。攻撃者は AI の事業者の API キーを狙っていたと Railway はみている。復号されたデータには 1,852 人の連携トークンが含まれ、盗まれた鍵での不正な利用は約 74 万米ドルと見積もられた。

<strong>認証情報が正しく出されることは、それを使う作業が本物であることを示さない。</strong>

## 2. 通った操作

- **通った操作**: 2 つある。1 つ目は、CI/CD 向けの OIDC の交換で、短時間だけ有効なクラウドの認証情報が攻撃者に出されたこと（10 月 21 日 03:26 UTC）。2 つ目は、オーケストレーションの機械のディスクにあった長く有効な認証情報で、KMS に対して環境変数の復号を求め、それが通ったこと（同日 04:42〜05:14 と 06:36〜07:15 UTC）。その前段で、ビルド用の認証情報が、ビルドの Temporal に信頼された呼び出し元として受け付けられ、353 件のビルドの履歴が読まれた。
- **受け付けた側に届くもの**: 一般に、OIDC の交換を受けるクラウドの側には、作業の身元を示すトークンが届き、信頼の設定の条件に合えば認証情報を出す。条件そのものが誤っていれば、その作業が本来の配置かどうかは届かない。KMS の側には、正しい認証情報と復号の依頼が届く。どの配置のための復号か、何件の環境にまたがるかは届かない。
- **公表されていないこと**: ビルド基盤の脆弱性の細部と、OIDC の設定のどこが誤っていたか（Railway は第三者のソフトウェアの脆弱性について、開発元と責任ある開示を進めているとしている）。どのクラウドの事業者の KMS か。復号された個々の変数の数（記録は環境の単位）。攻撃者が誰か（Railway は FBI の IC3 に届け出た）。外部の調査会社の調査は続いている。

## 3. 実行前の照合

経路を問わず区別できる条件は、クラウドの認証情報を出す前、と秘密情報を復号する前に、その依頼がどのリポジトリのどの配置の作業かを、信頼の設定の一致や手元の鍵とは別の配置の記録で照合することである。

- **誰が承認を出すか**: 基盤を運用する会社の、配置の持ち主。どのリポジトリのどのブランチの、どの配置の作業が、どのクラウドの環境に、どの権限で届いてよいかを決め、配置の記録として、CI/CD やビルドの認証情報では作れない形で残す。
- **どこで照合するか**: 2 か所ある。OIDC の交換でクラウドの認証情報を出す手順と、KMS に復号を求める手順。信頼の設定の条件に合っても、配置の記録と結びつかない交換は保留する。正しい鍵の復号でも、記録にない配置のための復号や、多くの顧客の環境にまたがる復号は保留する。
- **何が残るか**: どの作業が、どの配置の記録で、どの環境の値を復号したかの記録。鍵のサービスとは別に残し、どの顧客の値が復号されたかを、環境の単位より細かく後から確かめられる形にする。

検知は働き、最初の警報から約 17 時間で、復号に使われた認証情報は止められた。それでも、OIDC の交換と KMS の復号は、正しい認証情報として通った。CI/CD の信頼の設定が、正しい手続きで悪い作業を通した事案に [TanStack](https://lemma.frame00.com/ja/critical/briefs/014-tanstack-oidc-trusted-publisher/)（正規の OIDC の公開者で署名された悪性のパッケージ）、開発の基盤の内部への入口が外の認証から開いた事案に [Vercel](https://lemma.frame00.com/ja/critical/briefs/059-vercel-contextai-oauth/)（従業員が AI ツールに渡した OAuth）がある。[PocketOS](https://lemma.frame00.com/ja/critical/briefs/007-pocketos-cursor-db-deletion/) は、同じ Railway の API を AI エージェントが呼んで本番のデータベースを消した別の事案である。今回は、基盤の内側で、認証情報が次の認証情報を呼び、顧客の秘密情報の復号まで届いた。

## 4. Lemma でできること

**Lemma は、実行前の照合を、クラウドの認証情報を出す手順と、秘密情報を復号する手順に組み込む。** 侵入を見つけるのではなく、交換と復号がどの配置の作業のためかを、実行の前に照合する。

### 注意したい業界・業務

- **業界 · 開発者・エージェント運用**: 顧客のアプリと秘密情報を預かるホスティング・CI/CD の基盤と、そこに API キーを置く開発チーム。1 つの基盤の内部の認証情報から、多くの顧客の秘密情報に届く。
- **業界 · AI導入（業種横断）**: AI の事業者の API キーを環境変数に置いてアプリやエージェントを動かす会社。盗まれた鍵は、そのまま利用料の請求につながる。
- **業務 · アカウント・権限の管理**: CI/CD の OIDC の信頼の設定、サービスアカウントの権限、機械に置く認証情報の期限。
- **業務 · データへのアクセス**: 暗号化された秘密情報の読み出しと、鍵管理サービスでの復号。

### いまの対策と Lemma の違い

今回の経路は 3 列すべてを通った（ビルドの認証情報での内部の呼び出し → OIDC の交換 → 長く有効な鍵での復号）。列は、それぞれの段で何が実行されるかで分けている。

| 対策 | ビルドの認証情報での内部の呼び出し | OIDC の交換でのクラウドの認証情報 | 長く有効な鍵での復号 |
| --- | --- | --- | --- |
| ビルドの隔離（1 ビルドごとの仮想機械） | 一部 | 効かない | 効かない |
| 短時間だけ有効な認証情報 | 効かない | 一部 | 効かない |
| 呼び出し元ごとの復号の範囲の制限 | 効かない | 効かない | 一部 |
| **Lemma（実行の前の照合）** | 一部 | 効く | 効く |

ビルドの隔離は、ビルドから基盤の機械に出ることを難しくするが、今回は隔離が一部破られた。短時間だけ有効な認証情報は、使える時間を縮めるが、信頼の設定が誤っていれば出され、その時間の中で次の認証情報が取られた。呼び出し元ごとの復号の範囲の制限は、オーケストレーションの機械のように、仕事として復号が要る呼び出し元からの復号は通す。Lemma は、認証情報の正しさではなく、交換と復号が配置の記録と結びつくかを、実行の前に照合する。ビルドの認証情報は多くのビルドで共有されていたため、その列は、呼び出しにどのビルドかが記録として添う場合に限って働く。

注：Lemma の照合が働くのは、OIDC の交換と KMS の復号の手順に照合を組み込み、配置の記録を CI/CD とビルドの認証情報とは別に管理する場合に限る。配置の記録を作れる権限まで取られた場合や、記録にある配置の作業そのものが乗っ取られた場合は通りうる。表は何を照合しているかの比較で、今回の事案で止まったかどうかを示すものではない。Lemma は、侵入を検出・防止するものではなく、鍵を失効させるものでも、不正な利用額を取り戻すものでもない。

### 点検チェックリスト

預かった秘密情報の復号について、組織で確認する 3 項目

- 秘密情報を復号できる認証情報が、どの機械やサービスに、どの期限で置かれているかを一覧で確認できるか。
- 復号の操作を、呼び出し元と対象の環境ごとに記録し、どの顧客の値が復号されたかを後から特定できるか。
- 基盤の側で秘密情報が流出したとき、自社の API キーをどの順で替えるかが、手順として決まっているか。

## 5. 事実と時系列

- **当事者**: Railway（米国・開発とホスティングの基盤）。インシデント報告は 2026 年 11 月 10 日に同社のブログで公表され、10 月 22 日の予備報告に続くもの。外部の調査会社の調査は続いている。
- **起きたこと**: Railway によれば、攻撃者は 10 月 20 日 07:28 UTC に、ビルド基盤の未知の脆弱性でファイルシステムの隔離を一部抜け、ビルドのサーバーが内部の一部のシステムに使う認証情報を得た。ビルドの Temporal はこの認証情報を信頼された呼び出し元として受け付け、攻撃者は 353 件のビルドの履歴（秘匿された変数を含む）を読み、キャッシュ用のスナップショットから社内のモノレポの写しを得た。10 月 21 日 03:26 UTC、CI/CD の OIDC の信頼の設定の誤りから短時間だけ有効なクラウドの認証情報を得て、内部の認証情報と SSH の鍵を取り、オーケストレーションの機械に入った。その機械のディスクには、環境変数を復号できる長く有効な認証情報があった。攻撃者は 04:07〜05:21 UTC にデータベースから暗号化された変数を取り出し（変数の名前を、AI の事業者の鍵に当たる正規表現で選んでいた）、04:42〜05:14 と 06:36〜07:15 UTC に KMS で一部を復号した。
- **気づいた経緯**: ビルドの成果物を置く登録のサービスへの異常な API の呼び出しの警報で、10 月 20 日 13:58 UTC に当番の技術者が呼ばれた。Railway はビルドを 2 回止め（10 月 20 日 17:03 と 21 日 07:22 UTC）、10 月 21 日 07:14 UTC にクラウドの認証情報をすべて止め、固定の認証情報を失効させ、復号の機能を止めた。攻撃者は 09:24 UTC に追い出された。インシデント報告によれば、攻撃者は 10 月 18 日からダミーのアカウントを作っていた。
- **影響と対応**: 環境変数のいずれかが復号された可能性があるのは、最大で 1.85%（約 100,000）のワークスペース（上限の値）。復号されたデータには 1,852 人の連携トークン（持ち込みのエージェントの鍵と GitHub の OAuth トークン）が含まれ、Railway はすべてを再設定し、盗まれた認証情報での Railway へのログインは見つかっていないとした。盗まれた鍵での不正な利用は約 74 万米ドルと見積もられ、Railway は事業者と払い戻しを進め、応じない事業者の分は自社で負担するとした。顧客のデータベースへのアクセスは、調査では示されていないとしている。
