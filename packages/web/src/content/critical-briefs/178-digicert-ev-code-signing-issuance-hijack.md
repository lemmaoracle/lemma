## 1. 要点

DigiCert の報告では、攻撃者はサポートの担当者の端末に入り、サポートの画面から、審査を通って受け取りを待っていた注文の発行コードを取り出した。正規の組織の名前で EV コード署名証明書が発行され、その一部がマルウェアの署名に使われた。

申し込んだ組織の審査は正規の手順で通っており、発行コードと審査済みの注文があれば、証明書は受け取れた。審査そのものは破られておらず、横取りされたのは最後の受け渡しである。

<strong>受け取りのコードを持っているだけで証明書が渡るなら、審査が正しく行われても、証明書は審査を受けた相手ではない者の手に渡る。</strong>

## 2. 通った操作

- **通った操作**: 審査を通った EV コード署名証明書の注文に対する、証明書の受け取り（鍵の生成と発行）。攻撃者は、サポートの画面で取り出した発行コードを使い、複数の顧客のアカウントと、複数の発行元の CA にわたって証明書を受け取った（DigiCert の報告）。
- **受け付けた側に届くもの**: DigiCert の報告では、受け取りで確認されるのは、発行コードと、それに対応する審査済みの注文である。コードは「持っている者が使える」性質のもので、受け取る者が審査を受けた組織の人かは届かない。一般に、署名された側（ソフトウェアを実行する側）にも、正規の組織の名前で発行された有効な署名が届き、中身からは見分けがつかない。
- **公表されていないこと**: 攻撃者が誰か。署名されたマルウェアが、どこで、どれだけの利用者に届いたか。証明書が使われた日（DigiCert は、使われた日を追っていないとしている）。2 台目の端末に監視の仕組みが入っていなかった理由（DigiCert は、記録の保存期間を過ぎていて分からないとしている）。

## 3. 実行前の照合

経路を問わず区別できる条件は、受け取りの依頼が審査を受けた契約者の登録済みの管理者から来たかを、発行コードとは別に、証明書を受け渡す前に照合することである。

- **誰が承認を出すか**: 審査を受けた契約者の登録済みの管理者。受け取りの依頼が自分たちのものかを、注文やコードとは別に登録した連絡先や端末で承認する。認証局のサポートの担当者や、コードを持っているだけの者の操作は、この承認にならない。
- **どこで照合するか**: 審査済みの注文に対して、証明書を作り、トークンに渡す前。受け取りの依頼を契約者の承認と結び付けられないとき（コードだけが使われたなど）は、発行せずに保留にする。
- **何が残るか**: どの注文の証明書を、誰の承認で、どの受け取りの依頼に渡したかの記録。あとから、どの証明書が契約者の手に渡ったもので、どれがそうでないかを分けて、失効の範囲を決められる。

検知は働いていた。1 台目の端末は翌日に見つかって封じ込められ、研究者からの問題報告で証明書は順に失効されたが、それは証明書が発行され、署名に使われた後である。信頼された署名そのものが、出どころを照合されないまま受け入れられた事案に、[xz utils](https://lemma.frame00.com/ja/critical/briefs/082-xz-utils-backdoor-identity-provenance/)（権限を得た保守者が、署名済みの正規のリリースに裏口を入れた）と、[SecondFi](https://lemma.frame00.com/ja/critical/briefs/089-secondfi-signing-sdk-provenance/)（署名のコードが、監査を経ていない SDK に差し替えられたと外部解析が指摘した）がある。

## 4. Lemma でできること

**Lemma は、実行前の照合を、認証局が審査済みの注文の証明書を受け渡す段に組み込む。** 申し込んだ組織の審査や、端末への侵入の検知の代わりではなく、その後で、受け取りの依頼が審査を受けた契約者の承認と結び付くかを、発行の前に確認する。

### 注意したい業界・業務

- **業界 · 開発者・エージェント運用**: コード署名証明書で自社のソフトウェアに署名し、配る組織。自社の名前で、自社が受け取っていない証明書が発行されうる。
- **業界 · 調達・サプライチェーン**: 証明書・鍵・アカウントを、審査や契約の後に、コードやリンクで受け渡すサービス。
- **業務 · 配信・送付**: 審査や承認が済んだものを、最後に相手へ渡す受け渡しの段。
- **業務 · アカウント・権限の管理**: サポートの担当者が、顧客の立場で顧客のアカウントを見られる機能。

### いまの対策と Lemma の違い

今回の経路は、1 列目から 2 列目へ続く。1 列目で止まらなければ、2 列目の署名は、正規の組織の名前による有効な署名として通る。3 列目は、発行の後の対応である。

| 対策 | 審査済みの注文の証明書の受け取り | 証明書によるマルウェアへの署名 | 発行の後の失効 |
| --- | --- | --- | --- |
| 申し込んだ組織の審査 | 効かない | 効かない | 関係しない |
| 担当者の端末の監視（EDR） | 一部 | 関係しない | 関係しない |
| 研究者の問題報告と失効 | 関係しない | 一部 | 効く |
| **Lemma（実行の前の照合）** | 効く | 効かない | 一部 |

審査は、申し込んだ組織が本物かを確認するもので、今回は正規に通っており、受け取る者が誰かは確認しない。端末の監視は、DigiCert の報告では 1 台目の侵害を見つけて封じ込めたが、2 台目には監視の仕組みが入っておらず、侵入を見つけるもので、受け取りの依頼そのものは見ない。研究者の問題報告と失効は、発行された証明書を無効にしたが、署名に使われた後に働いた。Lemma は、受け取りの依頼が審査を受けた契約者の承認と結び付くかを、発行の前に照合する。発行された後の署名は止めない。証明書を失効させることもしないが、どの証明書が契約者の承認を経たかの記録は、失効の範囲を決めるのに使える。

注：Lemma の照合が働くのは、認証局の受け渡しの手順に照合を組み込み、契約者の登録済みの管理者と連絡先をサポートの画面や注文の情報とは別に管理する場合に限る。契約者の管理者のアカウントそのものが乗っ取られている場合は、この照合を通りうる。登録済みの連絡先が書き換えられている場合も同じである。表は何を照合しているかの比較で、今回の事案で止まったかどうかを示すものではない。Lemma は、侵入を検出・防止するものではなく、証明書を失効させるものでもない。

### 点検チェックリスト

証明書・鍵・アカウントを受け渡すサービスで確認する 3 項目

- サポートの担当者が顧客の立場で見られる画面に、受け取りのコードなど、持っているだけで使える値が出ないようにしているか。
- 受け取りの依頼ごとに、誰の承認で、どの証明書や鍵を渡したかを、後から辿れる記録に残しているか。
- 自社の名前で発行された証明書の一覧を、自社が受け取った証明書と突き合わせる手順があるか。

## 5. 事実と時系列

- **当事者**: DigiCert（米国の認証局）。サポートの担当者 2 人の端末が侵害された。
- **侵入の入口**: 攻撃者は、顧客向けのサポートのチャットで、顧客のスクリーンショットに見せかけたファイルを送った。4 回は防がれ、5 回目で 1 台目の端末が侵害された。2 台目は同じ入口で侵害された（DigiCert の報告）。
- **取り出されたもの**: 担当者が顧客の立場で顧客のアカウントを見られるサポートの画面から、審査を通って受け取りを待っていた EV コード署名証明書の注文の発行コード。この機能では、アカウントや注文の管理はできないが、発行コードは隠されていなかった（DigiCert の報告）。
- **証明書**: 60 枚を失効した。発行元は DigiCert の CA 2 つと、GoGetSSL・Verokey の名前の CA の計 4 つ。うち 27 枚が攻撃者に関わると特定され（11 枚は研究者などからの問題報告、16 枚は DigiCert の調査）、残る 33 枚は、顧客の手にあると確認できなかったため、念のため失効した。受け取り待ちの注文は取り消された（DigiCert の報告）。
- **署名されたもの**: 研究者が特定した証明書は、「Zhong Stealer」と呼ばれるマルウェアの署名に使われていた（DigiCert の報告）。
- **DigiCert が挙げた要因**: 端末の監視の範囲がそろっていなかった。サポートの画面の機能の権限が絞られていなかった。発行コードが、持っている者が使える値として守られていなかった。サポートの窓口が、危険な種類のファイルを受け付けていた。
- **ほかの影響**: DigiCert は、ほかの社内のシステムが悪用された跡や、審査の情報が悪用された跡、コード署名以外の証明書の不正な発行は見つからなかったとしている。

### 時系列

- **2026-04-02**: 攻撃者が、サポートのチャットで担当者に不正なファイルを繰り返し送る。1 台目の端末で開かれる。
- **2026-04-03**: 1 台目の端末で監視の仕組みが検知し、封じ込める。この時点では、2 台目は侵害されていないと判断された。
- **2026-04-04**: 2 台目の担当者の端末が、同じ入口で侵害される（後の調査で判明）。
- **2026-04-05〜04-16**: 研究者などから、証明書の問題報告が順に届く。DigiCert は、それぞれ 24 時間以内に失効する。
- **2026-04-14**: 2 台目の侵害が見つかり、範囲が広がる。担当者のアカウントを止め、サポートの画面で発行コードを隠す変更を米国で入れる（翌日に API と EU にも）。
- **2026-04-17**: 最後に特定した証明書を失効する。失効の日付は、発行の日にさかのぼって設定された。
- **2026-04-18**: DigiCert が、Mozilla の Bugzilla に第一報を出す。
- **2026-04-28**: DigiCert が、事後報告の全文を出す（05-04・05-05 に改訂）。
- **2026-07-09**: DigiCert が、すべての対応の項目を終えたとして、報告の終了を求める。

> 本件の事実は、DigiCert が Mozilla の Bugzilla に出した事後報告と、その後の回答（一次）に拠る。2 台目の端末について、DigiCert は当初「監視の仕組みが正しく動いていなかった」と書き、05-04 と 05-05 の改訂で「入っていなかった」に直した。Help Net Security の報道は、Zhong Stealer を中国の犯罪の活動や暗号資産の窃取と結び付けている。ある研究者の報告が 2 台目の発見につながったとも伝えている。これらは報道の記述で、DigiCert の報告には無い。公表されていないことは、対策が無かったことを意味しない。

### 公表後の対応

- **DigiCert**: 発行コードを、サポートの画面と API の両方で隠した。サポートの画面の機能は読むだけにした。チャットと問い合わせの添付で危険な種類のファイルを止め、添付をサンドボックスで調べるようにした。端末の監視の登録を自動で突き合わせ、入っていない端末は社内のシステムにつながらないようにした。発行コードを、契約者の権限のある管理者だけが見られるようにした。21 の対応の項目をすべて終えたとしている。
- **DigiCert の約束**: 発行コードを、使い切りで、持っている者が使える値として、期限も含めて扱うとしている。DigiCert の回答では、発行コードの有効期間は 30 日だった。
- **業界の論点**: Bugzilla の議論では、CA/Browser Forum のコード署名の作業部会の議長が、認証局は発行の時点で、組織が後にマルウェアに署名するかを見分けられないと述べた。DigiCert は、今回と同じ時期に、サポートの窓口へのソーシャルエンジニアリングの試みが増えているとしている。
