## 1. 要点

改ざん版は、正規の Chrome ウェブストアから、利用者がすでに入れていた正規の拡張機能の更新として届いた。偽のサイトや偽のアプリからではない。

Trust Wallet の公表では、攻撃者は漏れたストアの API キーで改ざん版を直接送った。版は社内の承認と手作業の確認を通らないまま、ストアの審査を経て自動で公開された。破られたのは、会社の出金の鍵や承認者ではなく、利用者の手元で鍵を扱うソフトを配る経路である。

<strong>公開の鍵を持っているだけで新しい版が出せるなら、社内の承認を経ていない版も、正規の拡張機能の更新として利用者に届く。</strong>

## 2. 通った操作

- **通った操作**: ブラウザ拡張機能の新しい版（v2.68）の、Chrome ウェブストアへの公開。攻撃者は、漏れた API キーで改ざんした版を送り、版はストアの審査を通って自動で公開された（Trust Wallet の公表）。利用者の側では、ふだんの更新として新しい版が入った。
- **受け付けた側に届くもの**: 一般に、ストアに届くのは、開発者の API キーで認証された提出と、版の中身である。その版が、開発者の社内の承認と確認を経たものかは、キーからは分からない。利用者の側にも、正規の拡張機能の、ストアで公開された新しい版が届き、更新の経路からは見分けがつかない。Trust Wallet の公表では、改ざん版は読み込まれると、ウォレットの機密の情報を攻撃者が取り出し、無断で取引を実行できるようにした。
- **公表されていないこと**: 攻撃者が誰か。API キーが、開発のどの場所に、どのように置かれていたか。ストアの審査で何が確認されたか。改ざん版をストアに送った日時（報道は、公開を 12-24 の 12:32 UTC と伝えている）。抜かれた資産のうち、Trust Wallet に結び付かないアドレスの分の額（同社は追跡中としている）。

## 3. 実行前の照合

経路を問わず区別できる条件は、公開しようとしている版が社内の承認を経たものかを、公開用の API キーとは別に、ストアへの公開の前に照合することである。

- **誰が承認を出すか**: 社内で公開を承認する登録済みの担当者。どの版（ビルド）を出すかを、公開用のキーとは別に置いた鍵や端末で承認する。キーを持っているだけの者や、自動の公開の仕組み（パイプライン）の操作は、この承認にならない。
- **どこで照合するか**: ストアへの提出と公開の前。公開の仕組みが送ろうとしている版を、承認された版と照合する。一致しないとき（承認の記録が無い、中身が違うなど）は、提出せずに保留する。
- **何が残るか**: どの版を、誰の承認で、どの配布先に公開したかの記録。あとから、配布先に出ている版が承認を経たものか、手順の外から出たものかを分けられる。

検知は働いていた。流出は公開の翌日に研究者や提携先の警告で表に出て、同社は元の版に戻した版を出したが、それは改ざん版が利用者の手元に届き、読み込まれた後である。正規の配布の経路に、出どころを照合されないコードが入った事案に、[Polymarket](https://lemma.frame00.com/ja/critical/briefs/087-polymarket-frontend-supply-chain/)（フロントエンドの依存に、不正なコードが注入された）と、[SecondFi](https://lemma.frame00.com/ja/critical/briefs/089-secondfi-signing-sdk-provenance/)（署名のコードが、監査を経ていない SDK に差し替えられたと外部解析が指摘した）がある。審査は正しく通ったのに最後の受け渡しが横取りされた型に、[DigiCert](https://lemma.frame00.com/ja/critical/briefs/178-digicert-ev-code-signing-issuance-hijack/)（審査済みの注文の証明書を、攻撃者が受け取った）がある。

## 4. Lemma でできること

**Lemma は、03 の照合を、開発者が新しい版をストアへ公開する段に組み込む。** ストアの審査や、開発の環境への侵入の検知の代わりではなく、その手前で、公開しようとしている版が社内の承認と結び付くかを、公開の前に確認する。

### 注意したい業界・業務

- **業界 · 金融・FinTech**: ウォレット・取引・決済のアプリや拡張機能を、ストアから配る組織。利用者の手元で鍵や取引を扱うソフトの更新が、そのまま資産の流出の経路になる。
- **業界 · 開発者・エージェント運用**: ストアや配布先への公開を、API キーや自動の公開の仕組みで行う組織。キーが漏れると、社内の手順の外から版を出せる。
- **業務 · 配信・送付**: 新しい版を、ストアの自動の更新で利用者に届ける段。
- **業務 · 承認・決裁**: どの版を公開するかの、社内の承認と手作業の確認。

### いまの対策と Lemma の違い

今回の経路は、1 列目から 2 列目、3 列目へ続く。1 列目で止まらなければ、2 列目の更新は正規の拡張機能の更新として届き、3 列目の流出は利用者の手元で起きる。

| 対策 | ストアへの新しい版の公開 | 利用者の端末への更新の配布 | ウォレットの情報の取り出しと送金 |
| --- | --- | --- | --- |
| ストアの審査 | 一部 | 関係しない | 関係しない |
| 社内の承認と手作業の確認 | 効かない | 関係しない | 関係しない |
| 研究者・提携先の警告と元の版へのロールバック | 関係しない | 一部 | 一部 |
| **Lemma（実行の前の照合）** | 効く | 関係しない | 効かない |

ストアの審査は、届いた版の中身を見るもので、Trust Wallet の公表では、改ざん版は審査を通った。その版が開発者の社内の手順を経たかは見ない。社内の承認と手作業の確認は、同社の公表では、API キーで直接送られた版には通らなかった。キーだけで公開できる経路では、この手順を通らない版が出うる。研究者・提携先の警告とロールバックは、流出を表に出し、元の版に戻した版を届けたが、改ざん版が読み込まれた後に働いた。Lemma は、公開しようとしている版が社内の承認と結び付くかを、ストアへの提出の前に照合する。利用者の端末に届いた後の動きや、送金は止めない。漏れたキーを失効させることも、抜かれた資産を回収することもしない。

注：Lemma の照合が働くのは、ストアへの提出と公開の仕組みに照合を組み込み、公開用の API キーを、その仕組みだけが使える場所に置く場合に限る。公開用のキーがその仕組みの外で使える場合や、承認の担当者の鍵や端末そのものが乗っ取られている場合は、この照合を通りうる。表は何を照合しているかの比較で、今回の事案で止まったかどうかを示すものではない。Lemma は、侵入を検出・防止するものではなく、鍵を失効させるものでも、資産を回収するものでもない。

### 点検チェックリスト

アプリや拡張機能をストアから配る組織で確認する 3 項目

- ストアや配布先への公開に使う鍵を、開発の環境やリポジトリの秘密情報とは分けて置いているか。
- 配布先に公開されている版を、社内で承認した版と突き合わせる手順があるか。
- 公開ごとに、誰の承認で、どの版をどの配布先に出したかを、後から辿れる記録に残しているか。

## 5. 事実と時系列

- **当事者**: Trust Wallet（暗号資産のウォレット）。影響を受けたのは、ブラウザ拡張機能 v2.68 を 12-24〜12-26 に開いてログインした利用者。モバイルのアプリと、ほかの版の拡張機能の利用者は影響を受けていないとしている（Trust Wallet の公表）。
- **公開の経路**: Trust Wallet によれば、2025 年 11 月のサプライチェーンの事案「Sha1-Hulud」で開発の秘密情報（シークレット）が漏れ、攻撃者は拡張機能のソースコードと Chrome ウェブストアの API キーを得た。攻撃者はキーで改ざんした版を直接送り、社内の承認と手作業の確認を経ずに、ストアの審査を通って自動で公開された。同社はこの結び付きを「高い確度」としつつ、経路の調査は続いているとしている。
- **攻撃者の準備**: 攻撃者は、Trust Wallet に似た名前のドメインを登録して不正なコードを置き、改ざん版からそのコードを読み込ませた（Trust Wallet の公表）。
- **被害**: Trust Wallet に結び付く 2,520 のアドレスから資産が抜かれた。攻撃者の 17 のアドレスに、約 850 万ドルの資産が結び付く。攻撃者は Trust Wallet に結び付かないアドレスからも資産を抜いており、その分は追跡中としている（Trust Wallet の公表）。BleepingComputer は、同社が特定したアドレスを 2,596、被害の額を約 700 万ドルと報じた。
- **補償**: Trust Wallet は、影響を受けた利用者に自主的に補償するとしている。5,000 件を超える申し立てが届き、重複や不正なものも多いとみて、1 件ずつ審査している（Trust Wallet の公表）。

### 時系列

- **2025-11**: 「Sha1-Hulud」の事案で、開発の秘密情報が漏れる（Trust Wallet の見立て）。
- **2025-12-24**: 改ざんされた v2.68 が、正規の公開の手順の外から Chrome ウェブストアに公開される。報道は、公開を 12:32 UTC と伝えている。
- **2025-12-25**: 最初の資産の流出が公に報告される。研究者と提携先、社内の仕組みが警告を出す。
- **2025-12-26**: 11:00 UTC 以降に拡張機能を開いてログインした利用者は、影響を受けないと同社はしている。
- **2025-12-29**: BleepingComputer が、同社の CEO の説明として、v2.68 は社内の手作業の手順で出したものではなく、漏れた API キーで提出されたとみていると報じる。
- **2025-12-30**: Trust Wallet が、事案のまとめを公表する（2026-07-17 に更新）。

> 本件の事実は、Trust Wallet のブログの公表（一次）に拠る。同社は、調査が続いているため数字は変わりうるとしている。アドレスの数（2,596）、被害の額（約 700 万ドル）、公開の時刻、API の止め方は BleepingComputer の報道による。このうち数字は、同社の公表（2,520、約 850 万ドル）と違う。公表されていないことは、対策が無かったことを意味しない。

### 公表後の対応

- **Trust Wallet**: 正しい v2.67 に戻した版を v2.69 として出し、利用者に更新を求めた。公開の権限と関わる API の認証情報を止め、公開の権限を絞った。拡張機能の公開、公開の仕組みと道具への権限、監視に、守りを足したとしている。公開の流れ、依存関係の検査、権限の管理、認証情報の管理と入れ替え（ローテーション）の決まりを見直しているとしている。
- **補償の手続き**: 公式のサポートのフォームで申し立てを受け付け、申し立ての確認のために、拡張機能の v2.70 で確認のコードを出す予定としている。同社は、秘密の鍵やシードフレーズ、パスワードを尋ねることはないとして、なりすましに注意を呼びかけている。
- **報道**: BleepingComputer は、同社が公開の API を 2 週間止めたこと、不正なコードを置いたドメインが登録事業者に止められたこと、同社の名前を使ったフィッシングのドメインがシードフレーズを求めていたことを伝えている。
